§0总览与决策记录

决策(2026-07-16):平台优先。原"ISCAS 2027 投稿(2026-10-13)前不动平台工程"的红线由项目负责人解除;已知后果——ISCAS 的实测-PPA 门槛可能赶不上、论文顺延——已确认接受。自此主线切换为搭建 RDMA 研究平台。

本文档的范围:单台 VCU118 把 RoCE WRITE 链路跑通。即:软件通过 PCIe BAR 发起 Work Request → roce_stack 生成合法 RoCE v2 帧(含 ICRC)→ 经 Corundum 数据面从 QSFP0 发出 → DAC 线环回 QSFP1 → RX 路径解析、放置 payload、产生 ACK → 回到 TX 侧完成确认。全程 bit-exact 可验。

以下内容刻意后置,不在本文档展开:

  • ConnectX-5 互操作(实验室已有卡)——14 项工程检查单与建链细节见仓库 review-stage/PLATFORM_BALBOA_CX5_NOTES.md Part B;
  • BALBOA 发表数字对比——三层对比表见同一文档 Part A;
  • codec 插入(transform + deflate)与 dual-length verbs 研究段——平台跑通后的研究阶段(§7)。
事实基线本手册中的接口位域、文件路径、常量与行为断言,均来自 2026-07-16 前后对一手来源的核验(源码逐文件 grep、官方文档、BALBOA 论文全文深读)。个别来自论文图表像素测量的数值一律标注"约"。未核实处明确写"以仓库为准"。

§1平台架构

一句话:把 roce_stack 当一颗"协议引擎芯片"用——README 原话是"RoCE 周边模块需用户自行提供以集成进自己的项目",我们的周边模块 = 软件 doorbell 垫片 + 内存胶水 + Corundum app_block 注入/截获。

关键设计事实(全部已在源码核实)

  • 当前物理设置:板不插 PCIe 槽,台面独立供电,仅 JTAG + UART(USB)连电脑(用户约束 2026-07-16)。所以 doorbell / 写 WQE / 写 payload / 读回全部走调试链路,不走 PCIe。走 PCIe 的完整 verb(host DMA、SQ ring、驱动)= §7 的后续流程,本文档不实现。
  • SQ 是推入式,不含 WQE-fetch 机器。s_rdma_sq 是 metaIntf 流,协议引擎不会主动去 host 内存取 WQE——真实 RNIC 的"doorbell 通知 + 硬件 DMA 取 WQE"前端在 Coyote 里由 shell + 驱动代劳。我们分两档补:L0(本文档范围)= JTAG-to-AXI Master(Xilinx jtag_axi IP)驱动 AXI-Lite 垫片:host 侧 Vivado hw_server 的 run_hw_axi 直写 WR 字段寄存器 + 敲 doorbell,零 PCIe、零驱动;L1(后置,走 PCIe)host DRAM 放 SQ ring + producer-index doorbell + app_block DMA 取 WQE。L0 足够单 WRITE 正确性验证;per-WR 延迟/CQE 时序 + 吞吐扫频需要 L1(见下一条 payload 说明)。
  • payload 取数是硬件自动的,但喂数当前走 JTAG(慢)。SQ 命令给出本地地址与长度后,协议引擎自己从 m_rdma_rd_req 发 (vaddr, len, ctl) 读命令、等数据从 s_axis_rdma_rd 流回、切 PMTU、打包发送——这部分永远是线速的。当前 payload 由 JTAG-to-AXI 预先写入片上 staging(URAM/BRAM);单 WRITE 的出线时序仍是真实线速(payload 已在片上,doorbell 一敲即发)。但逐条 JTAG 敲 WQE 不能测吞吐(WRITE 间隔被 JTAG 主导)→ 吞吐/延迟扫频需要"payload 预载 + 片上 replay 引擎背靠背发",属研究阶段。
  • ICRC 在仓库里。hdl/common/icrc.sv + hls/crc/;该栈与 ConnectX-5 互操作过,线上格式为合法 RoCE v2,Wireshark 可解。
  • Corundum 侧的官方插入点是 mqnic_app_block:TX/RX 三层 AXI-Stream 钩子 + DMA 接口 + AXI-Lite,专为在数据面内做自定义处理设计(《三框架入门》§3)。
  • 环回两端都是本板 CMAC → FEC/autoneg/对端兼容类问题在本阶段结构性不存在,全部推迟到 CX-5 互操作阶段。

  1. 完整 verb over PCIe(用户明确的"后续流程"):把板插进主机 PCIe 槽,启用 Corundum 的 PCIe/DMA + mqnic 驱动,做 L1 doorbell = host DRAM SQ ring + producer-index doorbell + DMA 取 WQE。这才解锁 per-WR 延迟组成、CQE 时序、以及真实 host→板 payload 通路。(③ 已先行落地片上 SQ 环 + producer doorbell,07-18 板上首验;host DRAM/PCIe 部分仍后置)
  2. 片上 replay 引擎(吞吐扫频的前提):payload 预载 staging + 片上描述符环背靠背发 WRITE,让 CMAC 侧计数器测到真实吞吐-消息尺寸曲线——绕开 JTAG 的慢速瓶颈,不必等 PCIe。
  3. 重传缓冲 DDR4/URAM 重置:把 HBM 假设换掉,受控丢包(app_block 故障注入)下验证 go-back-N——这同时是 dual-length-under-retransmission 实验的地基。(③ 已完成 URAM 再安置 + B9 仿真闭案 07-18;板级受控丢包注入器待做)
  4. ConnectX-5 互操作:14 项检查单 + ~200 行 libibverbs 对端 harness(可先用 Soft-RoCE/rxe 调通)→ review-stage/PLATFORM_BALBOA_CX5_NOTES.md Part B。
  5. codec 插入:channel-major/byte-transpose 变换 + Vitis DCL 动态-Huffman gzip CU(gzip_compress_multicore_stream.cpp,ap_ctrl_none 纯 AXI4-Stream)上 TX payload 路径;第一步用自描述 chunk(NetZIP 式)拿通路。(④ 已仿真级完成 07-19:定版 8 核/16KB gzip CU 存转发挂 staging Port A,双长度面全环打通;报告见仪表盘 ④ 行)
  6. dual-length verbs 研究段(论文核心):SQ 命令与协议管线扩展 wire-length/app-length 双记账(RETH/DMA-len/PSN/重传存储/放置/CQE),压缩载荷重传正确性;对比"引擎上游自包含压缩"与"verbs 内压缩"两种放置。BALBOA 对比数字与可比性 caveat → 同文档 Part A。
