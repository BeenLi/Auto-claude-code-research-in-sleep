§1这个实验回答什么问题

Stage A 是整个五阶段计划的第一道闸门,它同时回答三个独立的问题——任何一个是"否",后面所有阶段的计划都要改写:

#问题为什么关键答案

§2实验原理

2.1 csim 是什么,它验证什么、不验证什么

HLS 的 C 仿真(csim)是把 HLS C++ 源码当普通软件编译执行(2025.2 里用 clang-16),流(hls::stream)退化为线程内 FIFO,#pragma HLS 全部被忽略。所以:

  • 它验证的是算法/协议语义:状态机转移、字段组装、字节搬运的逻辑对不对;
  • 它不验证:时序、流水线行为、接口握手时序、以及任何由 pragma 决定的东西(那些属于 csynth/cosim,即 Stage B 之后)。

对 Stage A 的目标(Q1–Q3)这恰好足够:Q1 是编译器/头文件层问题,Q2 是 API 层问题,Q3 是协议语义问题——三者都在 csim 的验证边界内。

2.2 为什么"一帧 WRITE 的解剖"就能当协议初检

看似只验了一个包,实际上这一帧的每个字节都要求引擎内部一整条链路全部正确才能产生:

这就是"单帧解剖"的杠杆:用一个可完全预测的最小激励,让输出的每个字节都有唯一正确值。我们把 QP/PSN/rkey/地址/payload 全部设成可辨识的"签名值"(如 0x1122334455667788、0xA0+i),帧里凡是出现这些值的位置,都能反推"哪个环节把哪个输入搬到了哪里"。

2.3 对照组设计

直接跑自带测试台大概率失败(代码考古显示它针对旧 API)。我们把这一步保留为对照组而不是跳过:如果它失败在"链接器/头文件找不到",说明工具链有问题(Q1 危险);如果失败在"函数签名不匹配",说明工具链没问题、只是 TB 陈旧(Q1 安全,Q2 需自建)。失败的形态本身就是证据。

§4我们做了什么(三步)

  1. 环境侦察与配置生成。确认 2025.2 无 vitis_hls、锁定 vitis-run --tcl 入口;发现独立 clone 下 cmake 流断链(FindVitisHLS.cmake 缺失)且官方流程本就没有 csim 目标 → 绕开 cmake,手工从 4 个 .hpp.in 模板生成配置头,手写 csim tcl。
  2. 对照组:原样编译自带测试台。结果符合预判:9 个设计源文件全部编译通过,失败只发生在 test_rocev2.cpp 内部,且失败形态是"函数候选要 19 个参数、调用给了 13 个"与"APP_WRITE 未声明"——即纯 API 陈旧,工具链无恙。Q1 由此基本得证,Q2 确认需自建。
  3. 自建最小测试台并迭代到通过。按 §3.2 的闭环写 my_write_tb.cpp(约 250 行),期间踩到并解决 4 个技术障碍(§6 发现 1–4),最终 csim 官方判定 0 errors,帧落盘。

§5结果怎么看

5.1 先学会读原始输出

TX 流每拍是一个 512-bit(64 字节)word,带 keep(64 位,每位标记对应字节是否有效)和 last(帧尾标记)。print() 按 data[7:0] 先出——实测这就是线序(wire order),即打印出的第一个字节就是网络上先发出的字节,多字节字段直接从左向右按大端读,无需再做字节序翻转(这是本实验确立的读数规则,后续阶段沿用)。

5.2 帧解剖(实测原始数据 + 逐层注释)

┌ IPv4(20B)────────────────────────────────────────────────────────────
│ 45 02 00 7c 00 00 40 00 64 11 00 00 0b 01 d4 d1 0b 01 d4 d2
│ └45=v4/头长5×4B  └00 7c=总长124  └11=UDP  └源 11.1.212.209 └目的 11.1.212.210

5.3 三道自洽性检查(比逐字段更有力的证据)

  • 长度三角自洽:IP 总长 124 = 20(IP)+8(UDP)+12(BTH)+16(RETH)+64(payload)+4(ICRC);UDP 长 104 = 124−20;keep 标记的有效字节 = 120 = 124−4。三个独立来源的长度互相咬合,且差值恰为 ICRC 的 4 字节——说明引擎预留了 ICRC 位置只是没填内容。
  • 签名值溯源:VA 来自 txMeta.raddr、R_key 来自 qpContext.r_key、DMALen 来自 txMeta.len、PSN 来自建 QP 时的初值——四个值经四条不同的内部通路到达帧中,全部正确,即 §2.2 链路图上每个环节都被证实。
  • 计数器交叉验证:regIbvCountTx=8 而 TB 只发了 1 条 SQ 命令——这不是 bug:本分支 RETRANS_EN 默认开,TB 不回 ACK,重传定时器按协议把同一帧重发了 7 次。帧 dump 里 word2/3 与 word0/1 逐字节相同,与该解释完全一致;crc_drop=psn_drop=0 则说明 RX 侧没有误触发。一个"意外"的读数反而额外白送了重传状态机在动的证据。
PASS 判定(对照手册 Stage A 通过标准逐条) csim 构建通过(官方 "CSim done with 0 errors")✓ · 单 WRITE 帧字段核对:UDP:4791 ✓ / BTH 0x0A ✓ / RETH DMALen=64(+VA/R_key/PSN/destQP)✓ / payload 逐字节 ✓ · 工具链版本定版:全项目锁定 2025.2 ✓。字段核对由执行者解码 + 复核者按原始 hex 独立重解一致。

§6发现与有效性边界

6.1 实验中的四个技术发现(后来者会再踩的坑)

发现 1:模板宽度参数的单位是 bit,不是 byte。
rocev2<DATA_WIDTH> 里 DATA_WIDTH=512;配置系统里同名变量却以字节计(64)。用 <64> 实例化会因 crc<512,0> 等显式实例化缺失而链接失败——单位混用是这套代码的固有陷阱。
发现 2:头文件里有一个"幽灵声明"。
rocev2.hpp 声明了 2 参模板 rocev2<WIDTH, INSTID> 但从未定义;真身是 rocev2.cpp 里的 1 参版本。TB 必须自己前向声明 1 参版本、并靠 rocev2_top 的隐式实例化来链接。这是"声明与实现漂移"的活教材,也再次印证该分支处于活跃重构期。
发现 3(唯一的真版本漂移):2025.2 的 hls::stream<T> 要求 T 可默认构造。
新实现内嵌 T _data 成员,而 psnPkg 只有带参构造 → TB 里构造 stream<psnPkg> 直接编译失败(设计本体只传引用,不受影响)。绕法:把引用绑到零初始化的静态存储上、从不消费(这三个 DBG 流只在 RX 路被写)。这是 Q1 的完整答案:2025.2 可用,且漂移面被精确圈定在"TB 构造流对象"这一种场景。
发现 4:DBG_IBV 是无条件宏。
ib_transport_protocol.hpp:40 里直接 #define,不是编译开关——顶层因此固定多 3 个调试流参数(stock TB 报"要 19 个参数"的直接原因)。对 Stage C 的意义:SV 侧 roce_stack.sv 的 `define DBG_IBV 与之呼应,垫片接口按 19 参形态设计。
发现 5(07-16 复盘"没建连查表验证啥"时追源码补录):"QP 上下文"内部拆成三张表;virtual_address 字段被复用为部分更新的魔数操作码。
① 一条 qpContext 默认同时写两处:state table(状态 + 双向 PSN)与 MSN 表(rkey,经 if2msnTable_init);连接表(remote_qpn/IP/UDP 端口)由 ifConnReq 单独灌——不存在一张统一 QP 表。state table 自己的 r_key 写入在本分支被注释(state_table.hpp:207),RETH.rkey 的真实供数是 MSN 表(generate_exh 读 msnMeta.r_key,ib_transport_protocol.cpp:1577)。② qpContext 没有"命令"字段,该分支把 virtual_address 当带内操作码:0xDEADBEEF → 本条只更新 rkey(只写 MSN 表);0xFEEDBEEF → 只更新 remote PSN(state table 选择性更新);其余值 → 常规全量建 QP(ib_transport_protocol.cpp:2120-2131)。对 Stage C 的意义:QP 配置写入器按三表语义设计;这两个魔数禁止当真实 VA 传入(会被静默解释成部分更新,QP 建不起来且无任何报错);反过来调试期可用 0xFEEDBEEF 重同步 PSN 而不重建 QP。

6.2 本实验证明不了什么(诚实边界)

  • ICRC 正确性:csim 不物化 ICRC 字节(长度预留、keep 掩掉),校验和字段也为 0。ICRC 生成逻辑是否正确本实验无证据 → 已列为 Stage B(RTL 仿真)的第一记录点,用软件参考实现对拍。
  • Ethernet 层:帧从 IPv4 起——MAC 头由栈外的 mac_ip_encode 添加,属 Stage B/D 的验证范围。
  • 时序与握手:csim 里 dataflow 靠反复调用推进,任何"流水线深度/反压/时钟域"的结论都不能从本实验得出。
  • RX 路径:本实验只走了 TX;RX 解析/放置/ACK 生成留待 Stage B 的 TX→RX 回灌。

§7结论与对下一阶段的输入

结论:Stage A PASS。三个问题全部得到肯定答案:2025.2 工具链可用(锁定,不装 2022.2);活跃分支可被外部驱动(自建 TB,自带 TB 弃用);协议引擎 TX 链路在语义层正确(单 WRITE 帧逐字段+三道自洽检查通过)。

  1. ICRC 对拍是第一记录点(本实验的最大空白);

  5. 读数规则沿用:print() 输出即线序。
