§1回答什么问题

  1. shell 在真板上活不活? Stage D 的两处再扎根(mmcm_rst=0、MMCM 出 250M)、CMAC 自主 bring-up、Si570 参考时钟共享、GT/QSFP 物理层——行为仿真全部覆盖不到,只有上电见分晓。判据 = DS34(done)+ LED5/6(双 CMAC rx_aligned)。
  2. 没有 USB 直通,能不能交互驱动 jtag_axi? 单向 SVF 只能烧板不能对话。案头写的 MPSSE 版 XVC 桥(xvc_mpsse_server.py)首次见硬件——它撑不撑得起 hw_server 的 discovery + run_hw_axi?
  3. 全环闭不闭? A→D 四级 golden 传递后,最后一跳:同一 c_write64 序列经真芯片、真光笼、真铜缆,placement/ACK/CQE/计数器是否与仿真一致(15 项 CHECK)。

§2原理

两相推进:先踩实证过的地板,再走新路

相 1(SVF+openocd 烧写、LED 判读)是本台架唯一被证过的路径,它单独就能裁决 shell 的时钟/复位手术是否成功;相 2(XVC 桥)是新路,失败也不动摇相 1 的结论。这个切分让"板子坏了"与"桥写错了"两类故障天然隔离。

台架调试方法论:对照组 + 最小自测 + 取证日志

桥的每个故障都用三件工具定位:①已知好对照(openocd 同 FTDI 读 IDCODE)锚定硬件无辜;②最小自测客户端(绕开 Vivado 直接说 XVC:74b IDCODE 探针、2000b 跨批 TDI 回声探针)把"桥对不对"变成可独立判定的命题;③取证日志(每 shift 记 nbits+TMS/TDI/TDO 哈希;hw_server 侧开 -ljtag2,discovery,xvc 追踪)让"hw_server 为什么不满意"从猜测变成读日志。四颗雷(§4)全部按此流程钉死,无一靠试错碰运气。

参考实现即规范:openocd 为什么不死

FT232H 的命令/回读 FIFO 各 1KB。"写完一批再读"的桥在回读积压超限时会让 MPSSE 引擎停摆 → 命令写永久阻塞(USB 写超时)。openocd 从不楔死的结构性原因是它把 OUT 与 IN 的 USB 传输并发提交,芯片侧回读被持续排空。桥最终采用同构方案(读端独立线程),此后零崩溃——比较参考实现的结构,而非只抄它的参数。

LED 读法

DS34 = 配置 done;LED5/6 = 两条 CMAC rx_aligned(相 1 核心判据);LED7 心跳 = 250MHz 时钟树活着(MMCM 手术成功的直接可视证据);LED0–4 = shell 静态状态位。上电到全绿数秒,无需任何软件干预——CMAC bring-up FSM 与 RS-FEC 双端同栈天然一致。

§6发现与边界

E1JTAG-SMT2-NC 的 MPSSE layout 是 0x00e8/0x60eb,不是 hs2 的 0x0088/0x008b。

ADBUS5/6/7 三个缓冲使能必须全驱高、ACBUS5/6 输出低。只驱 bit7 时"半使能":TCK/TMS 不达链、TDO 恒高——症状与"板子没上电"无法区分,极易误诊。对照 openocd 自带 cfg 原文是唯一可靠信源(记忆不是)。

E2FT232H 写完再读会死锁;并发排空是结构性要求。

回读积压 >1KB → MPSSE 引擎停摆 → 命令写超时(Errno 60)→ 会话死。批量调参(2048→448)不解决——必须写/读并发(openocd 的 async URB 同构)。同时 SEND_IMMEDIATE(0x87)+ latency=2 消除 16ms 延迟计时器等待。

E3hw_server 对 XVC 目标开多条连接;XVC 服务器必须多客户端。

jtagpoll 节点轮询与 open 数据通道各占一条;单客户端服务器谁后到谁饿死,且饿死者在服务器日志不可见(accept 积压)。Xilinx 参考 xvcserver 也是单客户端——它能用大概率是时序侥幸,不要抄。

E4open_hw_target -xvc_url 在本环境死路;auto-open-servers 是正解。

labtools 发起的 XVC open 在 hw_server 2025.2(容器/Rosetta)下恒报 "No devices detected",与桥实现、hw_server/cs_server 新旧、重烧全部无关(hw_server 内部日志显示节点明明建立)。启动参数 -e "set auto-open-servers xilinx-xvc:host:port" 走一等电缆代码路径,一次成功。此坑价值一小时。

E5设计跑起来后 JTAG 10MHz 边际化。

配置前 openocd 10MHz 扫链干净;配置后同参数报 IR capture error(off-by-one 特征),3MHz 恢复干净。250MHz 逻辑 + GTY 活动改变 TDO 时序余量。后续所有 openocd 操作(扫链/SVF)统一降 adapter speed 3000;XVC 桥本就 3MHz 不受影响。

E6JTAG-AXI 吞吐画像:讨论式操作足够,数据面不可用。

逐位 XVC(3 字节命令/位)下 discovery ~1M 位耗时十余秒,单次 AXI 读回 ~百 ms 量级;write64 全流程(含 16 次 payload 预载写)分钟内完成。这是控制面/调试面带宽——8K/12K payload 预载(2048 次写)是分钟级,吞吐测量不归 Stage E(手册既有边界)。

边界:本夜只跑 c_write64(write8k/12k 的 FIRST/MIDDLE/LAST 板上版为可选加测);B9(请求方定时重传)依旧 OPEN——环回 ACK 即时返回测不到;retrans 楔死运维边界不变(真丢帧 = CNT_RETRANS≠0 + TX 停摆,唯一恢复是重烧,今夜未触发);链路状态可读寄存器位仍未实现(本夜靠 LED 目视,列平台可用期第一项);XVC 桥为调试基础设施,非交付物性能路径。

§7结论与移交

结论平台首光达成:Stage D shell 在真板一次点亮(时钟/复位手术 + CMAC 自主 bring-up + DAC 链路全验证),自研 XVC 桥打通交互式 run_hw_axi,c_write64 全环 15/15 PASS——单 VCU118 RoCE WRITE 平台 Stage A→E 五门全部关闭。golden 五级传递:同一帧序列从 csim 到真铜缆逐字节一致(ICRC ccbeb072 五代不变)。

移交平台可用期(优先级序):

  1. 链路状态寄存器位(rx_aligned 读回,替代 LED 目视;需 D-2 门回归 + 重综合)——解除"必须有人看板子"的运维依赖。
  2. 可选加测:write8k/write12k 板上版(tcl 扩 STEP,预载分钟级为预期)。
  3. L1 doorbell(SQ ring + DMA WQE fetch)、retrans 缓冲 DDR4/URAM 再安置。
  4. CX-5 互通:先补 Ethernet encap/decap(D2/账本 A21),先打 Soft-RoCE/rxe,再上真卡(14 项检查单)。
  5. codec 插入(transform 引擎 + Vitis DCL gzip CU)→ dual-length verbs 研究期(未来论文核心)。
