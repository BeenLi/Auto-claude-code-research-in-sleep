§1帧格式:RoCE v2 就是跑在 UDP 上的 InfiniBand 传输层

层字段本平台取值 / 说明
Ethernetdst/src MAC, type=0x0800环回阶段静态配置;ARP 由 hls/arp_server 或静态表解决
IPv4src/dst IP, proto=UDProce_stack 顶层有 local_ip_address 输入;栈内 #define IP_VERSION 4
UDPdport=4791源码常量 RDMA_DEFAULT_PORT = 0x12B7(=4791),RoCE v2 的注册端口
IB BTH(12 B)opcode, destQP, PSN, ackreq…传输层头,每个包都有;opcode 编码"这是消息的第几段"(§3)
IB RETH(16 B)vaddr(8B), rkey(4B), DMALen(4B)只出现在 WRITE 的 FIRST/ONLY 包:告诉对端"写到哪、凭什么、总共多长"
payload—FIRST/MIDDLE 段严格等于 PMTU;本栈 PMTU=4096(硬编码)
ICRC(4 B)CRC32不变量 CRC:对"路由中不变的字段+载荷"计算,可变字段(TTL、DSCP/ECN、校验和等)按掩码规则替换后参与计算。接收端 ICRC 错 = 静默丢弃
调试要点(Stage B 勘误)本分支 RX 根本不校验 ICRC(crc.hpp:39 无条件 #define DISABLE_CRC_CHECK)——坏 ICRC 帧会被照常接受、放置、回 ACK,crc_drop_pkg_count 恒为 0(Stage B 实测)。计数器仍接 AXI-Lite,但排障时不要指望它;真正设防的是对端商品 RNIC(它会校验我们的 TX——我们的 TX ICRC 已与参考实现互证正确)。若未来需要 RX 设防:去掉该 define 重新综合,或在 SV 层加校验。

为什么Stage B 的核心工作就是逐字段校验 m_axis_tx 输出帧。注意上方勘误:本分支 RX 不校验 ICRC,环回平台内它不是故障源;但对端商品 RNIC(CX-5)会校验我们的 TX——互操作阶段"ICRC 错 = 静默丢包"仍是最阴的故障模式。 动手用 Wireshark 打开任一 RoCE v2 抓包(或 Stage B 产出的 golden pcap),手工核对 BTH 的 opcode/PSN/destQP 与 RETH 的 vaddr/rkey/DMALen;再手算一帧 ICRC 与工具比对。 入口源码 hdl/common/icrc.sv, hls/crc/ · Obsidian 003互联基础设施/rdma(ib_pack.h 逐字段笔记)

§2RC 语义:PSN / ACK / NAK / go-back-N

  • PSN(24-bit,每 QP 独立):发送侧每发一个包 +1;接收侧严格按序校验——收到"过去的 PSN"重发 ACK(重复包),收到"跳号的 PSN"回 NAK sequence error。
  • ACK / AETH:响应端用 ACK 包(BTH+AETH)确认;AETH 携带 syndrome 与 MSN(消息序号,多包消息计数)。ACK 是累积的。本栈实测(Stage C):响应方逐包回 ACK 不合并(>PMTU 每 4096B 一个 48B ACK),CQE 仍只一个;对端合并 ACK 的情形归 CX-5 互操作检查单。
  • go-back-N 重传:发起端收到 NAK 或超时,从出错 PSN 起整段重发。本仓库注意:coyote-TCP-RDMA 分支 RETRANS_EN 默认开启(fns master 才是注释掉的——Stage A 勘误);BALBOA 重构核的重传缓冲设计在 HBM 通道上,VCU118 无 HBM,平台已再安置到 URAM(见下方注记)。
  • 流控:该栈用 ACK 时钟化的按请求计信用(最大在途请求数为构建参数),不依赖 PFC——BALBOA 在有损交换网上就是这样跑的,我们的点对点环回更不需要 PFC。
时间线注记(07-18 已更新)早期文档说"环回阶段先跑无重传、一丢即挂"——那是 Stage B–E 首光阶段的状态,已过期。平台可用期工作项 ③ 已把重传缓冲再安置到 URAM(替换 tie-off,解楔死)并仿真闭案 Stage B 遗留 B9:丢 ACK → transport timer 约 626µs 超时 → 重传帧逐字节 = 原帧(线上 TX 抓包证明)。板级保持仿真证明(环回链路无丢帧注入器)。详见 platform-stage/DOORBELL_SQRING_RETRANS_DESIGN.md 与指南仪表盘 07-18 决策行。

§3WRITE 解剖 × 为什么 WRITE-only

一次 RDMA WRITE(消息长 L,PMTU=4096)在线上是:

L ≤ 4096      →  WRITE_ONLY   [BTH+RETH+payload+ICRC]
L > 4096      →  WRITE_FIRST  [BTH+RETH+4096B]   ← RETH 只在第一包
                 WRITE_MIDDLE [BTH+4096B] × n    ← 每段严格 = PMTU
                 WRITE_LAST   [BTH+尾段]

响应端内容无关地把字节放到 vaddr(经 rkey 授权),按 PSN 记账,回 ACK。两个直接推论:

  • WRITE-only 是够用的科研范围:KV 传输的主 verb 就是 WRITE;BALBOA 本身也只实现 WRITE+READ(无 SEND/ATOMICS)。READ 需要响应端状态机,后置。
  • WRITE_WITH_IMM 伏笔:普通 WRITE 在响应端不产生任何 CQE(不消耗 receive request)——纯环回内我们两端都可观测,无所谓;但将来对 stock 网卡(CX-5)做压缩载荷实验时,接收主机需要"到达通知 + 压缩后长度"——WRITE_WITH_IMM 恰好消耗一个预投递的 RECV 并交付带 32-bit imm 的 CQE,把压缩长度放 imm 里一举两得。设计从第一天就留这个口。
此刻为什么学 · 动手做什么
为什么Stage B 通过标准里"≥PMTU 多包切分正确"就是它;WITH_IMM 是未来对 stock 网卡做压缩实验的接收通知设计,要从第一天留口。平台可用期 ④ 的双长度面(WQE len=压缩长)也建立在这张分段图上——线长必须 ceil4(IBTA PadCount 现实)。 动手拿 12KB 消息手画包序列(含每包长度与 PSN),再与 Stage B 仿真输出对照;找出 len 恰为 n×4096 时的边界情况。 入口hls/fns_config.hpp(PMTU 常量)
