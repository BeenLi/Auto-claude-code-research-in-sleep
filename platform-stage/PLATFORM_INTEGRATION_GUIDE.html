单板 VCU118 上,以 Corundum NIC 为载体、fpga-network-stack roce_stack 为传输引擎、软件 doorbell 为前端,QSFP0═DAC═QSFP1 环回跑通 RDMA WRITE 的立即执行手册。

§0总览与决策记录

§1平台架构

一句话:把 roce_stack 当一颗"协议引擎芯片"用——README 原话是"RoCE 周边模块需用户自行提供以集成进自己的项目",我们的周边模块 = 软件 doorbell 垫片 + 内存胶水 + Corundum app_block 注入/截获。

关键设计事实(全部已在源码核实)

  • 当前物理设置:板不插 PCIe 槽,台面独立供电,仅 JTAG + UART(USB)连电脑(用户约束 2026-07-16)。所以 doorbell / 写 WQE / 写 payload / 读回全部走调试链路,不走 PCIe。走 PCIe 的完整 verb(host DMA、SQ ring、驱动)= §7 的后续流程,本文档不实现。
  • SQ 是推入式,不含 WQE-fetch 机器。s_rdma_sq 是 metaIntf 流,协议引擎不会主动去 host 内存取 WQE——真实 RNIC 的"doorbell 通知 + 硬件 DMA 取 WQE"前端在 Coyote 里由 shell + 驱动代劳。我们分两档补:L0(本文档范围)= JTAG-to-AXI Master(Xilinx jtag_axi IP)驱动 AXI-Lite 垫片:host 侧 Vivado hw_server 的 run_hw_axi 直写 WR 字段寄存器 + 敲 doorbell,零 PCIe、零驱动;L1(后置,走 PCIe)host DRAM 放 SQ ring + producer-index doorbell + app_block DMA 取 WQE。L0 足够单 WRITE 正确性验证;per-WR 延迟/CQE 时序 + 吞吐扫频需要 L1(见下一条 payload 说明)。
  • payload 取数是硬件自动的,但喂数当前走 JTAG(慢)。SQ 命令给出本地地址与长度后,协议引擎自己从 m_rdma_rd_req 发 (vaddr, len, ctl) 读命令、等数据从 s_axis_rdma_rd 流回、切 PMTU、打包发送——这部分永远是线速的。当前 payload 由 JTAG-to-AXI 预先写入片上 staging(URAM/BRAM);单 WRITE 的出线时序仍是真实线速(payload 已在片上,doorbell 一敲即发)。但逐条 JTAG 敲 WQE 不能测吞吐(WRITE 间隔被 JTAG 主导)→ 吞吐/延迟扫频需要"payload 预载 + 片上 replay 引擎背靠背发",属研究阶段。
  • ICRC 在仓库里。hdl/common/icrc.sv + hls/crc/;该栈与 ConnectX-5 互操作过,线上格式为合法 RoCE v2,Wireshark 可解。
  • Corundum 侧的官方插入点是 mqnic_app_block:TX/RX 三层 AXI-Stream 钩子 + DMA 接口 + AXI-Lite,专为在数据面内做自定义处理设计(§3)。
  • 环回两端都是本板 CMAC → FEC/autoneg/对端兼容类问题在本阶段结构性不存在,全部推迟到 CX-5 互操作阶段。

§2RoCE v2 协议入门

自足入门,适合组内共读。已熟 RDMA 者可跳到 §3;更深的协议笔记见 Obsidian 003互联基础设施/rdma(基于 rxe / ib_pack.h / Mellanox PRM 核验)。

2.1 帧格式:RoCE v2 就是跑在 UDP 上的 InfiniBand 传输层

层字段本平台取值 / 说明
Ethernetdst/src MAC, type=0x0800环回阶段静态配置;ARP 由 hls/arp_server 或静态表解决
IPv4src/dst IP, proto=UDProce_stack 顶层有 local_ip_address 输入;栈内 #define IP_VERSION 4
UDPdport=4791源码常量 RDMA_DEFAULT_PORT = 0x12B7(=4791),RoCE v2 的注册端口
IB BTH(12 B)opcode, destQP, PSN, ackreq…传输层头,每个包都有;opcode 编码"这是消息的第几段"(下节)
IB RETH(16 B)vaddr(8B), rkey(4B), DMALen(4B)只出现在 WRITE 的 FIRST/ONLY 包:告诉对端"写到哪、凭什么、总共多长"
payload—FIRST/MIDDLE 段严格等于 PMTU;本栈 PMTU=4096(硬编码)
ICRC(4 B)CRC32不变量 CRC:对"路由中不变的字段+载荷"计算,可变字段(TTL、DSCP/ECN、校验和等)按掩码规则替换后参与计算。接收端 ICRC 错 = 静默丢弃
调试要点(Stage B 勘误)本分支 RX 根本不校验 ICRC(crc.hpp:39 无条件 #define DISABLE_CRC_CHECK)——坏 ICRC 帧会被照常接受、放置、回 ACK,crc_drop_pkg_count 恒为 0(Stage B 实测)。计数器仍接 AXI-Lite,但排障时不要指望它;真正设防的是对端商品 RNIC(它会校验我们的 TX——我们的 TX ICRC 已与参考实现互证正确)。若未来需要 RX 设防:去掉该 define 重新综合,或在 SV 层加校验。

2.2 RC 语义:PSN / ACK / NAK / go-back-N

  • PSN(24-bit,每 QP 独立):发送侧每发一个包 +1;接收侧严格按序校验——收到"过去的 PSN"重发 ACK(重复包),收到"跳号的 PSN"回 NAK sequence error。
  • ACK / AETH:响应端用 ACK 包(BTH+AETH)确认;AETH 携带 syndrome 与 MSN(消息序号,多包消息计数)。ACK 是累积的。
  • go-back-N 重传:发起端收到 NAK 或超时,从出错 PSN 起整段重发。本仓库注意:fns master 的 RETRANS_EN 是被注释掉的(hls/rocev2/rocev2.hpp);BALBOA 重构核有超时+PSN 触发重传,但重传缓冲设计在 HBM 通道上——VCU118 无 HBM,重置方案见 §6。环回链路丢包率≈0,Stage B–E 可以先跑无重传模式,但要清楚:一旦丢一个包,该 QP 就挂死(接收端 NAK、发送端不重发)。
  • 流控:该栈用 ACK 时钟化的按请求计信用(最大在途请求数为构建参数),不依赖 PFC——BALBOA 在有损交换网上就是这样跑的,我们的点对点环回更不需要 PFC。

2.3 WRITE 解剖 × 为什么 WRITE-only

一次 RDMA WRITE(消息长 L,PMTU=4096)在线上是:

L ≤ 4096      →  WRITE_ONLY   [BTH+RETH+payload+ICRC]
L > 4096      →  WRITE_FIRST  [BTH+RETH+4096B]   ← RETH 只在第一包
                 WRITE_MIDDLE [BTH+4096B] × n    ← 每段严格 = PMTU
                 WRITE_LAST   [BTH+尾段]

响应端内容无关地把字节放到 vaddr(经 rkey 授权),按 PSN 记账,回 ACK。两个直接推论:

  • WRITE-only 是够用的科研范围:KV 传输的主 verb 就是 WRITE;BALBOA 本身也只实现 WRITE+READ(无 SEND/ATOMICS)。READ 需要响应端状态机,后置。
  • WRITE_WITH_IMM 伏笔:普通 WRITE 在响应端不产生任何 CQE(不消耗 receive request)——纯环回内我们两端都可观测,无所谓;但将来对 stock 网卡(CX-5)做压缩载荷实验时,接收主机需要"到达通知 + 压缩后长度"——WRITE_WITH_IMM 恰好消耗一个预投递的 RECV 并交付带 32-bit imm 的 CQE,把压缩长度放 imm 里一举两得。设计从第一天就留这个口。

上板环回首光(JTAG 驱动,无 PCIe)

等 DAC 线 + hw_server · 预计 1–2 周
目标
台面 VCU118(独立供电,不插 PCIe 槽),QSFP0═DAC═QSFP1 环回,纯 JTAG 驱动下单个 WRITE roundtrip bit-exact。这是"敲 doorbell 写 WQE 即可"的物理落地。
前置
Stage D 通过;DAC 线到货;VCU118 台面供电 + JTAG(USB)+ hw_server 通路已搭(不等线,现在就能做)。不需要:PCIe 插槽、PCIe 枚举、mqnic 驱动、BAR——全部推迟到 §7 的 L1/PCIe 阶段。
操作
  1. 板上电(自带电源)→ hw_server + Vivado 经 JTAG 连上 → 刷写 bitstream → run_hw_axi 读五个计数器(应全 0),确认 JTAG-to-AXI 地址图通;
  2. 插 DAC 成环,确认两个 CMAC 链路 up(两端同构,无 FEC/AN 兼容问题);
  3. 单 WRITE 序列全用 run_hw_axi:①写 QP 配置 → ②把 64B 已知 payload 写入 staging → ③写 WQE 字段寄存器(opcode=WRITE_ONLY/qpn/laddr/raddr/len=64)→ ④敲 doorbell 提交寄存器;
  4. 读回:run_hw_axi 读 placement 区(应等于 payload,bit-exact)+ 读计数器(ibv_tx/rx +1、crc_drop/psn_drop = 0);
  5. 覆盖分段:再发一个 >PMTU 的 WRITE(如 12KB,payload 预写 staging),验 FIRST-MIDDLE-LAST 序列在板上也 bit-exact;
  6. 可选埋点(强烈推荐,现在最便宜):BALBOA Fig-5 式分段延迟插桩(各流水段 first-byte-in→first-byte-out 的 cycle 计数器,经 AXI-Lite 读回)——单 WRITE 的出线时序是真实线速,可采;
  7. 负测试(app_block 内受控故障注入):丢一个包 → 确认无重传模式下 QP 挂死行为与计数器符合预期(§7 重传工作的动机数据)。
通过标准
PASS =纯 JTAG 驱动下单 WRITE(≤PMTU 与跨段各一)板级 roundtrip bit-exact;crc_drop/psn_drop 运行中为 0;计数器/延迟插桩可经 run_hw_axi 读回 → 平台链路宣告打通。注:吞吐/延迟扫频不在本阶段——逐条 JTAG 敲 WQE 无法反映真实 WRITE 间隔,吞吐需"payload 预载 + 片上 replay"(研究阶段)。
