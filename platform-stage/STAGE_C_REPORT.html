§1回答什么问题

Stage B 证明了协议引擎本身正确,但驱动它的是 TB 直插 metaIntf 的"上帝之手"。Stage C 回答三个问题:

  1. 主机视角够不够? 板上唯一的驱动通道是 JTAG-to-AXI(用户约束:无 PCIe)。一次 AXI-Lite 写发起的 WR,能否走完全环并且仅凭 AXI-Lite 读回(计数器 / CQE / placement 数据)判定正确?
  2. 自造的 surrounding modules 对不对? fns README 明说周边模块需用户自造。doorbell 预切分、payload 主动推流、非对齐 placement——这三件正是 Stage B 三条硬规范(B2/B3/B4)的落实处。落实得对不对,用 golden 传递性检验:同签名输入,输出帧必须与 Stage B 逐字节一致。
  3. >PMTU 的完整覆盖。 Stage B 只测了 FIRST/LAST(8KB);MIDDLE(12KB 中段)从未在 RTL 上跑过——切分 FSM 与栈内 PSN/placement 追踪在三段情形下是否正确?

§2原理

L0 doorbell:寄存器堆替代 WQE-fetch 机器

真 RNIC 的前端是"host DRAM 放 SQ ring + doorbell 通知 + 硬件 DMA 取 WQE";roce_stack 的 s_rdma_sq 是推入式 metaIntf 流,没有取数机器。L0 用 AXI-Lite 寄存器堆补位:WQE 字段各占一个寄存器,写 DOORBELL 寄存器即提交。这决定了它与驱动方无关——仿真里 TB 写,板上 jtag_axi 写,同一份 RTL。也决定了它测不了吞吐(逐条敲门被 AXI-Lite/JTAG 速度主导),这是手册早已声明的 L0 边界。

golden 传递性:三级同帧

Stage A(csim)→ Stage B(RTL 直驱)→ Stage C(AXI-Lite 全链)用同一套签名值(QPN/PSN/RKEY/RADDR/payload)。协议引擎是确定性的:若周边模块无损地重现了 Stage B 的输入时序语义,输出帧必须逐字节相同,ICRC 相同。任何一字节漂移都指向新造模块的缺陷。这比自造期望值严苛得多,也是"三条硬规范是否真正落实"的最强检验。

TX→RX 直连:Stage E 的仿真彩排

Stage B 的回灌是捕获后手工注入;Stage C 直接把 m_axis_tx 连到 s_axis_rx——这正是 QSFP0═DAC═QSFP1 环回的仿真化身。单栈自话:请求方发 WRITE,响应方(同一栈)收包、放置、回 ACK;ACK 环回给请求方,出 CQE。全程无人工干预,事件链的每一环都在计数器上留痕。

非对齐 placement:协议决定地址,胶水消化偏移

placement 的目的地址来自 RETH VA(协议侧语义),内存胶水无权要求对齐。签名 RADDR 0x334455667788 mod 256KiB = 0x27788,字内偏移 8——每个 64B 密集数据拍要按字节旋转后分裂成 56/8 两拍跨字写(字节使能)。发送侧则相反:payload 源地址由软件控制,L0 约束其 64B 对齐,省去读侧桶形移位。

§4做了什么

  1. 设计冻结。寄存器映射 + 三模块边界 + 三条 L0 约束:payload 源地址 64B 对齐(软件可控,省读侧桶形移位)、READ 不支持、doorbell 忙时打门被忽略(软件轮询 STATUS.busy)。切分 FSM 的每段严格按 Stage B 语义:CMD 被接受 → payload 全推完 → 下一段 CMD,len 为每命令段长(B4),local/remote 地址每段 +4096。
  2. RTL 三模块 + TB + 离线校验器一次成形(约 1100 行)。placement 写入器按"任意字节偏移"设计:每拍按 ptr[5:0] 旋转 + 字节使能,跨字则两拍(B口写优先,pusher 让行)。
  3. 对抗审查先于首跑。9 个并行 agent(5 个视角审查:契约缝落实 / xsim 地雷 / AXI-Lite 协议 / 数据通路算术 / TB 与校验器;每条候选发现再派怀疑者对抗验证)。产出:2 条确认(C-R1、C-R2,均 minor,见 §6)、2 条驳回(其中"偏移 40"的驳回顺带抓到一处注释算术错误——正确值是 8)。首跑之前能修的都修了。
  4. 编译一雷:LIBRARY_PATH(crt1.o,Stage B 老雷)——远端 Stage B 脚本早有 export,但入库副本漂移丢了这行。双向同步修复。
  5. 首跑即全绿。c_write64 一次通过全部自检;随后 8k/12k/magic 与三份离线 golden 校验一次通过。这不是运气:Stage B 把三条契约缝提前变成了硬规范,golden 工具箱直接复用。
  6. 审查修复 + 回归。落实 C-R1(doorbell/QP/conn 快照)与 C-R2(TB retrans 模型补拍偏移,Stage B TB 同源缺陷一并修);c_write12k 增加 mid-WR 突变探针;全部 4 用例 + 3 份 golden + Stage B write64/rx_loop 回归重跑,全绿。

§6发现与有效性边界

C1全环打通,板上视角自足。核心结论

一次 AXI-Lite 写发起的 WR 在 64B/8KB/12KB 三个规模走完 取数→分段→打包→回灌→放置→ACK→CQE;激励与判定全部经 AXI-Lite(= 板上 run_hw_axi 能做的动作集合)。doorbell→CQE ≈ 0.93µs(58 次轮询,64B)。

C2golden 传递性成立:AXI-Lite 全链零字节漂移。Q2 判定

c_write64 数据帧与 Stage B write64 F0 逐字节一致(ICRC 同为 ccbeb072),ACK 与 rx_loop F1 一致;c_write8k 两数据帧与 write8k F0/F1 一致。三条硬规范(结构体声明序打包 / 主动推流 / 预切分)在自造 RTL 中全部正确落实。

C3MIDDLE(0x07)首次 RTL 覆盖:无 RETH 中段连续放置正确。新覆盖

12KB → FIRST/MIDDLE/LAST,PSN 连续(80ce4e/4f/50),RETH 仅在 FIRST(DMALen=4096 = 每命令长度,B4 语义三段情形下再证),12288B placement 位精确——栈内部用 FIRST 的 RETH 状态为后续段推进写指针。

C4响应方逐包 ACK,非合并。行为事实

8KB 两数据包配两个 ACK,12KB 三配三;CQE 仍只有一个。线上开销:>PMTU 消息每 4096B 多一个 48B ACK 帧(环回场景无害)。CX-5 互操作观察项:IBTA 允许合并 ACK,对端很可能不逐包回——请求方一侧的 ACK 消化逻辑届时要靠 coalesced ACK 再验(检查单已有此项)。

C5非对齐 placement 方案验证:旋转 + 字节使能 + 两拍跨字。数据通路

落点 0x27788(字内偏移 8):每 64B 密集拍分裂 56/8 写入相邻两字,B口写优先、pusher 让行,三个规模位精确。遗留:URAM 双口 + 逐字节使能的综合推断(URAM288 BWE)待 Stage D 用真实综合确认;行为仿真不构成证据。

C6审查 C-R1(已修):提交时刻快照,挡住 mid-WR 寄存器突变。审查→修复

原实现中 dreq 的 pid/vfid/last 与 qp/conn 的 184b beat 由寄存器组合直驱——多段 WR 进行中(或 metaIntf ready 迟滞时)主机改写寄存器会污染在途消息/beat,违反 valid 期间数据稳定纪律。串行化的 TB 与 JTAG 时标踩不中,但 Stage D/E 的 PCIe/脚本主机可以。修复:doorbell 敲响时快照 pid/vfid/last,SUBMIT 时快照 184b;c_write12k 加突变探针(敲门后立刻改写 pid=63/last=0)验证快照生效——顺带解锁了合法的"WQE 预编程"用法。

C7审查 C-R2(已修):TB retrans 模型多拍写全部落在同一 64B 窗口。审查→修复

行为模型存储侧缺拍偏移(读侧有),>64B 的重传缓冲存储会塌缩成最后一拍——一旦发生重传回放,回放帧是垃圾,把可诊断的重传事件变成脏帧迷雾。Stage B TB 同源缺陷(从未被激发,不影响任何已记录判定)一并修复;Stage B write64/rx_loop 回归通过。残留:Stage B TB 的 cmd/数据同沿竞态未合并进单进程(Stage C TB 已合并),记录在案。

C8流程发现:入库脚本漂移 + 一处注释算术错误。已修

(a) 远端 run_xsim.sh 的 LIBRARY_PATH 修复未回流入库副本 → Stage C 首编译踩同一雷;已双向同步。(b) "落点偏移 40"应为 8(0x27788 mod 64)——审查驳回其功能影响时抓到,注释已正。教训:远端修的每一行必须当天回流仓库。

有效性边界

  • L0 范围:RDMA WRITE only;READ 的取数命令被计数吞掉;不支持 SEND/IMM。吞吐/延迟扫频不在本阶段(JTAG/AXI-Lite 逐条驱动,payload 预载 8KB 就占 ~25µs 仿真时)。
  • pusher 源地址 64B 对齐是 L0 约束(仿真有断言);doorbell 忙时打门被静默忽略(软件轮询 busy)。WQE_OPCODE 寄存器是登记项、不驱动线(切分 FSM 决定 opcode)——审查判为文档疣,已在映射表标注。
  • 环回是自话:单栈同时当请求方与响应方,PSN 初值天然一致;双栈/真对端的 PSN 不一致、乱序、丢包等在 Stage E(环回仍自话)与 CX-5 互操作阶段才有意义。RX 侧 ICRC 校验在本分支被编译殿(B5)——环回里 TX ICRC 正确性靠离线复算兜底。
  • retrans buffer 仍是 TB 模型;B9(请求方定时重传在 RTL 窗口未观察到)仍开放——本轮环回 ACK 即时返回,retrans=0 属预期,不构成对 B9 的解答。
  • 行为仿真不证 PPA:URAM 推断、250MHz 时序、FIFO 替身换真 IP,全部归 Stage D。

§7结论与移交

PASS 判定对照手册 Stage C 通过标准逐条:① 一次模拟 AXI-Lite 写发起的 WR 走完"取数→分段→打包→回灌→放置→ACK→m_rdma_ack"全环 ✓(三规模);② 输出帧与 Stage B golden 逐字节一致 ✓(64B/8KB 直接对拍,12KB 结构化 + ICRC);③ 计数器经 AXI-Lite 可读且数值正确 ✓(栈五 + 垫片六,两套互证)。另加四项超出标准的证据:MIDDLE 覆盖、非对齐 placement、魔数警戒、mid-WR 突变探针。

移交 Stage D(载体集成 + 综合)

  1. 集成单元就是 roce_l0_top:一个 AXI-Lite 从口(接 jtag_axi)、一对 512b AXIS(接 CMAC 胶水)、一组 mem 口(retrans buffer 再安置:URAM/DDR4 选型)。
  2. 载体决策先行(手册 §5-D 第一件事):rev100 Corundum 拆 PCIe 依赖 vs 裸 CMAC shell。
  3. 综合观察项:URAM 双口 + 字节使能推断(C5);HLS Fmax 估计 151.9MHz vs 250 目标的 post-route 裁决(Stage B 移交项);FIFO 行为替身换 axis_data_fifo 真 IP。
  4. 寄存器映射即驱动文档:TB 的 cfg_qp_conn/preload/submit_wqe/poll_cqe 序列可逐行翻译成 run_hw_axi tcl(Stage E 的脚本骨架已经在 TB 里排练完毕)。

挂账
