§1回答什么问题

  1. 双长度可行吗? 研究主线(dual-length verbs)的第一块地基:WQE 携带压缩长度(与原始长度解耦)能否零改动走完 roce_stack 全环——RETH.DMALen 取压缩值、任意字节长度、>PMTU 由 doorbell 预切分、responder 内容无关地 placement。侦察结论"len 28 位端到端不透明"必须被数据证实。
  2. DCL 2024.2 内核真实可用吗? 用户 07-17 指定的首要验证点:AMD 已从 2025.x 删除 data_compression,2024.2 分支的内核在 2025.2 工具链下 csim/csynth 是否可用;更进一步——csim 绿是否等于 RTL 绿(dataflow 内核的经典陷阱)。
  3. 硬件变换等价吗? E0 的 α 声称(bf16 chan_bt 0.708 / e5m2 chan 0.721)建立在 python 变换上;RTL 用地址生成器重新实现,必须证明逐位等价,且 α 落点可解释。

§2原理

存转发是结构必然,不是偷懒

doorbell 在 0x70 推环时刻就把 seg_len 同时锁进 SQ meta(→RETH.DMALen)与 pusher 命令(rdma_doorbell_l0.sv:287-321);而动态 Huffman 的输出长度只有压完才知道。因此"先压进 staging、读出 LEN_OUT、再发 WQE"是唯一不改栈的结构。CU 的输出长度经内核 TLAST 拍的 TUSER 带出(axi_stream_utils.hpp:124-131),与收集器字节计数交叉自检。

变换 = 纯地址置换 → 读侧地址生成器,零中间缓冲

E0 的 chan(channel-major)与 chan_bt(再加字节平面拆分)都是纯字节置换(layout.py:49-54 + floatsplit.py:142-149)。staging URAM 是随机访问的,于是变换退化为按置换序读字节:三层计数器(plane p / channel c / row r),chan_bt 取 p 外环、chan 取 p 内环,地址 = SRC + ((r<<hd_log2 | c)<<item16 | p),全移位无乘法。等价性由 §2 第三条的 golden 判据直接裁决。

三重恒等式 + 两级 golden

判据设计为一条恒等链,每一环排除一类故障:CU 输出 ≡ csim golden(变换+内核+写回正确)→ placement ≡ CU 输出(WQE/分段/环回/placement 无损)→ 线上载荷 ≡ CU 输出(逐段拆帧后重组,覆盖非 64B 尾段与 pad)→ stock 解码 ≡ 变换输入(commodity-decode 故事的字面验证)。实验揭示第一环对多块输入过强(§6 P4-3):8 核并发使 RTL 打包顺序与顺序执行的 csim 产生合法编码差异——golden 纪律遂修订为两级:单块字节恒等,多块解码逐位恒等(check_codec.py)。

Port A 复用:借主机的空闲窗口

staging Port A 仅在主机触碰 0x8xxxxx 窗口时活跃;CU 讲同一套 5 信号 32b 协议,由 roce_l0_top 二选一(doorbell 绝对优先,CU 仅在 stg_host_active 低时发拍)。对照 rdma_uram_staging.sv:84-91 的读管线逐拍推演:CU 在 T 发读、T+2 采样,采样值只依赖 T+1 周期的 RAM 输出寄存器——主机 T+1 的强拍影响 T+2/T+3,写操作在 no_change 模式下不动 douta,T 同拍冲突被门控排除 → 无需重放机制即 race-free。代价是 3 cycles/byte 的读速,对仿真与 JTAG 台架完全无感(吞吐是研究阶段命题,不是本阶段命题)。

§4做了什么

设计先行:三路侦察 → 设计文档 → 4 视角对抗评审

侦察(内核契约 / 插入点 / 数据与基准)钉出三个关键前提:WQE len 端到端不透明(压缩长 WR 零改栈)、Port A 空闲窗口可借、E0 变换粒度是整 chunk 而非每 32KB 块(α 对照的正确姿势)。设计文档(CODEC_INTEGRATION_DESIGN.md)过 4 视角评审 + 对抗验证:唯一 MAJOR(64B 写回与 32b 总线矛盾)被验证员降级为文档措辞问题——实现侧已改为 32b 协议(staging 因此零改动);4 个 MINOR 全部闭环(chan/chan_bt 环序区分、背靠背测试、err_len 措辞、doorbell-忙碌期约束的软件化决策)。

Gate 1(csim):2025.2 一把过,并买到一个 α 决策

7 项 roundtrip 全过、TUSER 长度定律成立。blk16 决策:32KB chan_bt 在 blk32 下 α=0.772(单棵树跨 plane0/plane1 熵段),16KB 块边界恰落 plane 边界 → 0.716,反超软件 V3(0.724);e5m2 与 256KB 中性。核数不变性:1 核与 8 核输出对全部四种输入 cmp 逐字节一致——核数是纯吞吐旋钮。256KB(E0 粒度)α=0.7005,与 E0 声称 0.708 同粒度贴合,数据管线正确性得证。

Gate 2(csynth)与 Gate 3(RTL 集成):六颗雷,逐一取证

csynth 1.5 分钟通过;cosim 设施在本环境损坏(P4-6)改由集成 xsim 直接裁决内核 RTL 健康。RTL 集成期间按"探针取证→根因→修复→回归"处理六雷(§6):其中 1 核死锁(P4-1)由 20µs 粒度探针钉死"喂完 32KB、吐 48 字节后永久沉默",根因直指 zlib_compress.hpp:404-471 的 NUM_BLOCKS 缩放 FIFO 深度公式;icrc 4B 粒度(P4-2)由 placement 缺口的零填充模式(缺 38 字节 = 末拍 42B 之载荷部分)反推到 icrc.sv:735-860 的枚举链空洞。修复后定版 8 核/16KB(= AMD 出厂测试的 gzipc_16KB 配置)。

全量门禁

run_gate_p4.sh:Stage C 4 测 + 8 项对认证 golden 的字节不变性 → Stage D 10 测(含 d_retrans_b9/d_retrans_b9_multi 及其线上重传帧数据检查)→ per-flow golden ×3 → codec 3 测 + check_codec.py 三份字节级校验 → GATE_P4_DONE fail=0(codec/logs/gate_p4.log)。

§6发现与有效性边界

P4-11 核配置 RTL 死锁 —— csim 绿 ≠ RTL 绿已定版规避

DCL 内核内部 FIFO 深度随 NUM_BLOCKS 缩放(c_thriceNumBlocks=3N、c_blckEosDepth=N²+N,zlib_compress.hpp:404-471):N=1 时深度 3/2,第二个顺序块经同一核即楔死(探针:喂完 32KB、吐 48B 后 kin r1/kout v0 永久沉默)。csim 的 hls::stream 无界(其自报最大占用 4355 ≫ 3)故看不见。AMD 只出厂测试 8 核。定版 8 核/16KB = AMD 测试包络;核数不改输出字节(cmp 证明)。教训入手册故障表:dataflow 内核必须 RTL 级验证。

P4-2icrc 重插入只处理 4B 粒度末拍 keep —— IBTA PadCount 现实浮出CU 侧按契约补齐

icrc.sv:735-860 的重插入枚举链只有 keep=4,8,…,60,64 字节各臂,无 default:keep=62(压缩长 23486 → 尾段 3006,mod 4 = 2)落空洞,末拍从线上消失(placement 尾部 38 字节补零,首个差异 @23448 与拆帧长度 23448 互证)。本质是 IBTA 契约:RoCE 载荷按 PadCount 补齐到 4B,栈从不自发非 4B 帧——平台史上第一个非 4B 倍长帧是压缩流发出的。修复走契约而非改认证栈:CU 末 4B lane 补零(写粒度=4B lane,pad 永不跨 lane),驱动侧 len=ceil4(LEN_OUT)。入 CX-5 互操作检查单(奇长度 PadCount 语义)。

P4-3多块输入下 RTL 输出 = 合法替代 gzip 编码(≠csim 逐字节)golden 纪律两级化

32KB(2×16KB 块)时 RTL 输出比 csim 长 +16B(bf16)/+1B(e5m2),首差在块 1 编码区内——8 核并发 + 共享 treegen 的到达序使打包时序相关;解码逐位恒等已证(两例均 gzip.decompress == 变换输入),α 差 <0.1%。单块(4KB)保持逐字节恒等。推论(载荷>16KB 板上同理且逐次运行可变):板上 codec golden 必须 decode-based,不能 byte-based。

P4-4F_IDLE case 臂缺失 —— default 覆盖 start 迁移已修

feed 引擎 case 无显式 F_IDLE 臂,start 周期里 default: f_state<=F_IDLE 在同一 always_ff 中晚于 start 块执行,最后非阻塞赋值获胜 → CU 永不启动。与 P3 的 sq_fetch 声明初始化冻结同类:SV 块内赋值顺序之坑,第二次入账。

P4-5HLS ROM .dat 按运行目录解析已布置

内核 11 个 ROM 以 $readmemh("./gzipc_cu_*.dat",…) 引用,按 xsim 运行目录而非 RTL 目录解析——需复制到两个 sim 运行目录;build#4 综合可见性是遗留 watch 项(Vivado synth 的解析基准不同)。

P4-6HLS cosim 设施在本环境损坏改道验证

cosim 的 AESL 死锁监控设施 C 编译失败(xsim_53.c,与 Stage B 的 LIBRARY_PATH 修复无关,另缺 zip 工具)。未纠缠:集成 xsim 直接编译运行同一批内核 RTL,回答了 cosim 存在的问题("内核 RTL 仿真健康")且证据等级更高(在真实集成环境中)。

有效性边界(诚实清单)

  • 仿真级:未上板(codec 综合 = build#4,未做;HLS slack 估计 −1.90 @4ns,Stage B 先例说明估计悲观,兜底 = CU 独立降频时钟域——存转发全解耦使 CDC 只在 CU 边界)。
  • 吞吐未测且未优化:读侧 3 cyc/B 是正确性期取舍;100G 线速命题属研究阶段。
  • B9 × codec 未组合测试:压缩 WR 的段与普通 WR 无异(retrans URAM 按段镜像、内容无关),结构性成立但未单独跑"丢 ACK + 压缩载荷重传"——如实记为未测项。
  • 约束面:head_dim 限 2 的幂(E0 全体模型满足);LEN_IN ≤ 2¹⁸−1;mode≠raw 要求 LEN_IN 整除 head_dim×itemsize(E0 对齐门同款);doorbell 忙碌期勿发与 DST 重叠的 WQE(软件约束,与"poll busy 再 doorbell"同类,已写入 doorbell 头注释)。
  • α 语义:硬件路径 α 引用本报告实测值(0.7167/0.7366/0.7005),不得转引 E0 的 0.708/0.721(粒度不同,D6 纪律)。
