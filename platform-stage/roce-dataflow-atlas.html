rdma_mux_retrans — 重传复用器与三条流

把 HLS 核的一个取数命令口(s_req_net)按三种场景分流—— 向用户请求 READ 响应数据、把发送的 WRITE payload 存底进重传缓冲、丢包时从缓冲回放—— 并把三路 payload 汇合成一条发包数据流(m_axis_net)送回 HLS 核打包。

1WRITE 发送:用户自发推 payload,tee 一式两份(发包 + 存底) 2READ 响应:先发描述符请求,用户回填数据 3重传:从缓冲回放,不打扰用户 控制(seq 队列给数据 Mux 编程) 汇合数据 / 混合命令

1WRITE 发送 — 请求环节被省掉

  1. HLS 核在 s_req_net 发取数命令(actv=1, !rd),命令 Mux 不转发给用户(req_user.valid=0),只生成 m_req_ddr_wr 存底命令,len 入 seq 队列。
  2. 用户提交 SQ 后自发把 payload 推进 s_axis_user_req,不等任何请求。
  3. 数据 Mux 按 len 计数切段,tee 点一式两份:一份经 net FIFO → m_axis_net 发包;一份经 ddr FIFO → m_axis_ddr 存进重传缓冲。
rdma_mux_retrans.sv L106–114 / L326–331 / L359–361

2READ 响应 — 完整的请求→回数握手

  1. 远端 READ 请求到达,要读的 vaddr/len 用户事先不知道。
  2. 命令 Mux(actv=1, rd)把描述符经 m_req_user(= m_rdma_rd_req)递给用户。
  3. 用户取数回填 s_axis_user_rsp → 经 net FIFO 发包。不存底(不进重传缓冲)。
rdma_mux_retrans.sv L97–105 / L317–324

3重传 — 缓冲回放,用户无感

  1. requester 定时器超时 / NAK,HLS 核发 actv=0 命令。
  2. 命令 Mux 生成 m_req_ddr_rd 回放命令(地址 = {vfid,pid,offs} 拼装)。
  3. 缓冲区把存底的 payload 从 s_axis_ddr 推回 → 直接发包,全程不打扰用户。

RoCEv2 核内部数据流 — RX/TX 流水线与五张状态表

HLS 核外层是 crc→IPv4→UDP 组帧壳(crc 实为直通,真 iCRC 由 roce_stack 的 Verilog 模块补算), 内层 ib_transport_protocol 是核心:上半 RX 流水线(meta 与载荷分离行进), 中间五张 per-QP 状态表,下半 TX 流水线(事件仲裁 → 头部拼装,自右向左)。 连线经 190 条断言对源码逐一核对。

载荷 / 包数据流 元数据 / 命令 / 事件 可靠性(重传表 / 定时器) 状态表查询 / 控制

RX:meta 与载荷分离行进

  1. rx_process_ibh 把每包拆成两路:meta(ibhMeta+PSN)走 rx_ibh_fsm,数据剥 BTH 后由 rx_process_exh 解析 RETH/AETH。
  2. rx_ibh_fsm 是守门员:epsn==psn 才按序放行;重复窗内 READ 重执行、WRITE 丢载荷但补 ACK、其余静默丢;完全无效 PSN 只 NAK 一次(retryCounter 门控)。载荷由 drop_ooo_ibh 整包丢弃。
  3. rx_exh_fsm 按 opcode 执行:WRITE 首包取 RETH.vaddr、后续从 msn_table 游标续写;READ 响应落地地址不来自包头,来自 retransmitter 前递的 laddr;READ REQ 交 handle_read_requests 切段。

可靠性闭环:登记 → 触发 → 重放

  1. 每个可重传包的表项由两半拼成:local_req_handler 登记 {addr,len,offs},generate_ibh 登记 {psn,opcode},按序配对存入 per-QP 链表(全局 2000 项池)。
  2. 两种触发:定时器超时(1/5/12/64ms 退避,上限 12 次)从链表头全量重放;RX 收 NAK 定点重放。重放事件回注 local_req_handler,优先于新 SQ,PSN 用原值。
  3. ACK 到达:释放表项 + 清定时器;READ_RESP FIRST/MIDDLE 只对表头增量更新(addr+=PMTU、len−=PMTU、psn+1)。RETRANS_EN 未定义则整套不编译。

rdma_flow — 发送窗口流控与 offs 的一生

坐在 SQ 命令面上的滑动窗:上游是 doorbell(Stage C)或 TB(Stage B)推来的 dreq_t 命令, 下游是 HLS 核的 s_axis_sq_meta。它按 {读/写, vfid, pid} 查 16 项指针表决定放行或阻塞, 放行时把窗口槽号写进 req_1.offs——这个 offs 一路贯穿 HLS 核、mux 和重传 URAM。

SQ 请求方向 ACK / CQ 方向 offs 槽号旅程 指针表读写

窗口机制:满窗即阻塞

  1. 窗口按 {读/写, vfid, pid} 独立——指针表地址的最高位区分 READ / WRITE,读写各一套 head/tail/issued。
  2. 满窗条件:issued && head==tail(16 个段在途);此时 s_req.ready 保持 0,上游被反压。窗空是同样的 head==tail 但 issued=0。
  3. 每收一个段 ACK 就 tail+1 退休一槽——隐含按序 ACK 假设。FSM 在 IDLE 里 ACK 优先于新请求,满窗一定能被 ACK 解锁,无死锁。单事务 3–4 拍(查表等 1 拍 RAM)。
  4. RDMA_N_WR_OUTSTANDING=16(lynx_pkg.sv:218);OFFS_BITS=6 但窗口只用低 4 位。
rdma_flow.sv L94 / L141–184

CQ 语义与上游分工

  1. 只有 last=1 的 ACK 进 CQ 队列 → 每个 WR 一个 CQE,多段 WR 的中间段 ACK 只退窗、不上报。
  2. roce_stack 自己不切大 WR:>PMTU 的切分在上游完成——Stage C 由 doorbell 预切 FIRST/MIDDLE/LAST,Stage B 由 TB 手工推两段;每段独立过 rdma_flow 拿一个 offs("one offs per segment")。
  3. doorbell 收 CQE 后 sq_compl++,且自身另有 SQ_BUDGET=8 的在途 WR 节流,与这里的 16 段窗口叠加。
