1. 两种自定义 SV 接口

1.1 metaIntf — 通用元数据握手

interface metaIntf #(parameter type STYPE = logic[63:0])
    (input logic aclk, input logic aresetn);
    logic  valid;
    logic  ready;
    STYPE  data;   // payload 类型由实例化时指定
    modport s (input valid, output ready, input  data);
    modport m (output valid, input  ready, output data);
endinterface
  • 语义:一次握手传一个 struct 或位向量,没有 tlast/tkeep。
  • 参数 STYPE 让同一个 interface 承载不同的 payload —— 常见形式是 logic[N-1:0] 的位向量或某个 typedef struct packed。
  • 命名约定:s_* 端口是 slave(数据流入 DUT),m_* 是 master(数据流出 DUT)。

1.2 AXI4S — 标准 AXI-Stream

interface AXI4S #(parameter AXI4S_DATA_BITS = ...);
    logic [AXI4S_DATA_BITS-1:0]   tdata;   // 数据
    logic [AXI4S_DATA_BITS/8-1:0] tkeep;   // byte-enable
    logic  tlast;
    logic  tvalid;
    logic  tready;
endinterface
  • 语义:多 beat 数据流,tkeep 表示尾节拍字节掩码,tlast 表示帧结束。
  • roce_stack 里所有 AXI4S 都是 512 bit(每 beat 64 B)。

2. 控制面(metaIntf)

一次握手一个 struct,用于 QP 配置、SQ 提交、CQ 通知。

端口metaIntf payload方向作用
s_rdma_qp_interfacelogic[183:0]slave写入 QP context(qpContext:qp_num / newState / remote_psn / local_psn / r_key / virtual_address)。由 HLS 内的 qp_interface 分发到 state_table 和 msn_table
s_rdma_conn_interfacelogic[183:0]slave写入 QP 的对端连接信息(remote_ip、remote_qpn、remote_udp_port),落到 conn_table
s_rdma_sqdreq_t(两个 req_t 打包)slaveSend Queue 请求提交。dreq_t = {req_1(rd, local), req_2(wr, remote)},一次投递一个 RDMA 操作
m_rdma_ackack_t(32 bit)master完成通知(CQ)。注意是 ack_t 而非 dack_t

qpContext 184 bit 打包(源码:third_party/fpga-network-stack/hls/rocev2/rocev2.hpp 附近的 qpContext)

TB 侧写入示例见 tb_stage_b.sv 的 push_qp_ctx / push_conn 任务(L294–L309)。

dreq_t / req_t / ack_t

定义在 lynx_pkg.sv(L340–L380):

  • req_t 128 bit:opcode / strm / mode / rdma / remote / host / dest / pid / last / vaddr / len / …
  • dreq_t = {req_1(rd, local), req_2(wr, remote)}(read/local + write/remote 一对)
  • ack_t 32 bit:opcode / strm / remote / host / dest / pid / vfid / …
  • dack_t = {ack, last}(本模块 CQ 用的是 裸 ack_t,不带 last)

3. 用户数据面(AXI4S + req_t 描述符)

用户应用(vFPGA / 上层逻辑)与 stack 之间的数据搬运。

端口类型方向作用
m_rdma_rd_reqmetaIntf<req_t>masterstack → 用户:请求用户提供 payload 的描述符(vaddr / len / last …)。只对 READ RESP 触发(Coyote/rdma_mux_retrans 语义)——WRITE payload 的取数不走这里
m_rdma_wr_reqmetaIntf<req_t>masterstack → 用户:告诉用户 "把 payload 放到这个 vaddr"(远端 WRITE 到达接收端时)
s_axis_rdma_rd_reqAXI4S 512bslave用户 → stack:WRITE 的 payload 输入(用户主动 push,见 tb_stage_b.sv L176–L196 的说明)
s_axis_rdma_rd_rspAXI4S 512bslave用户 → stack:READ 请求的响应 payload(收到 READ REQ 后由用户回填)
m_axis_rdma_wrAXI4S 512bmasterstack → 用户:远端 RDMA WRITE 到达后,把 payload 落地到用户内存

Coyote 的一点关键约定

rdma_mux_retrans 源码里的注释:"WRITE 的 payload 不通过 m_rdma_rd_req 请求,用户侧应在提交 SQ 命令后自发把 payload 推入 s_axis_rdma_rd_req"。 TB 的 push_payload() 就是按这个约定实现的。

4. 重传缓冲面(AXI4S + 96b/32b metaIntf)

模拟外挂 DDR/HBM,让 stack 在发出去以后能把 payload 存起来,遇到 NAK/超时时读回重传。 命令/状态用的是 Xilinx datamover 的 96/32 bit 格式。

端口类型方向作用
m_rdma_mem_rd_cmdmetaIntf<logic[95:0]>masterstack → 缓冲:读命令(addr + len + ctl)
m_rdma_mem_wr_cmdmetaIntf<logic[95:0]>masterstack → 缓冲:写命令
s_rdma_mem_rd_stsmetaIntf<logic[31:0]>slave缓冲 → stack:读状态
s_rdma_mem_wr_stsmetaIntf<logic[31:0]>slave缓冲 → stack:写状态
s_axis_rdma_mem_rdAXI4S 512bslave重传缓冲 → stack:把之前保存的 payload 读回来做重传
m_axis_rdma_mem_wrAXI4S 512bmasterstack → 重传缓冲:把即将发出去的 payload stash 一份

TB 里以字节数组 rbuf[] 作为重传缓冲的模型,配合 mem_rd_cmd / mem_wr_cmd 服务模型模拟 DDR。

6. 统计计数(valid + 32 bit data)

一组独立的"事件计数器"输出,每个都是 {valid, data[31:0]} 的脉冲/最新值风格:

信号含义
ibv_rx_pkg_count收到的 RoCEv2 报文数
ibv_tx_pkg_count发出的 RoCEv2 报文数
crc_drop_pkg_countiCRC 校验失败丢包数
psn_drop_pkg_countPSN 检查失败丢包数
retrans_count触发的重传次数

TB 里用 always_ff 把这些 pulse 锁存到 r_cnt_*,用于 phase 结束时统一打印。

8. 为什么区分 metaIntf 与 AXI4S

  • metaIntf 适合"一次一条的控制消息":QP 上下文、SQ 请求、CQ ack、DMA 描述符、DMA 状态。 这些消息本质上是一个 struct,一 beat 传完,不需要 tlast/tkeep,用 valid/ready + data 就够。
  • AXI4S 适合"多 beat 的字节流":网络报文、RDMA payload、重传缓冲搬运。 需要 tkeep 表尾节拍字节掩码,tlast 表帧结束。

因此 roce_stack 的端口很自然地就分成:控制面 = metaIntf + 数据/网络面 = AXI4S 两大风格, 用户数据面上还额外挂了一组 metaIntf<req_t> 作为 AXI4S 的"描述符伴随通道"。
