§1 三层全景对照

先给全图。同一件事(把一段本地数据写进远端内存)在三层世界里的机制分布:

§2 词汇精确化:WR、WQE、doorbell 是三个不同的东西

这三个词常被混用,严格区分后,很多项目里的设计(乃至 bug)会突然清晰:

  • WR(Work Request):API 层的请求对象,即 ibv_send_wr 结构体。活在用户内存里,可链成链表(*next),生命周期到 ibv_post_send() 返回为止。verbs 标准规定,跨厂商可移植。
  • WQE(Work Queue Element):队列层的硬件可消费编码。厂商私有二进制格式(如 mlx5 的 ctrl 段 + rdma 段 + data 段),由驱动写进 QP 的 SQ 环形缓冲(DMA 可达内存),网卡自己 DMA 取走。
  • doorbell:一次 MMIO 寄存器写,作用只有一个——告诉网卡"环里有新 WQE 了,去取"。

所以 ibv_post_send() 内部 = WR→WQE 翻译 + 写环 + 敲铃 三件事。对应到本项目:

项目里"SQ""doorbell""WQE"这些词的出处正是 verbs 世界;但要时刻记得本平台的"WQE"(txMeta)在抽象层级上比 verbs WQE 低一级(报文级 vs 消息级,见 §3 差异①)。

§3 txMeta ↔ verbs WQE 字段逐项对照

fns 的 SQ 命令格式声明于 third_party/fpga-network-stack/hls/ib_transport_protocol/ib_transport_protocol.hpp:220:

struct txMeta {
    ibOpCode    op_code;   // enum → 32 位
    ap_uint<16> qpn;       // Coyote 复合编码 {vfid, pid}
    ap_uint<1>  host;  ap_uint<1> lst;  ap_uint<6> offs;
    ap_uint<64> raddr;     // 声明序:raddr 在 laddr 之前(B2 的关键)
    ap_uint<64> laddr;
    ap_uint<32> len;  ap_uint<32> imm;      // 合计 248 位
};
verbs ibv_send_wrfns txMeta差异说明
opcode(消息级,IBV_WR_RDMA_WRITE)op_code层级不同:txMeta 用 IBTA 线上 BTH opcode(0x0A=WRITE_ONLY、0x06=FIRST、0x08=LAST,ACK=0x11)
sg_list[] + num_sgeladdr + len单一平坦缓冲,无散布列表(§7)
sg_list[].lkey—无 lkey / MR 保护概念(§5)
wr.rdma.remote_addrraddr对应;但高 16 位被 Coyote 征用为 {10'b0, strm, dest},会原样出现在线上 RETH VA 高位(§4)
wr.rdma.rkey—搬进 QP 上下文表:一个 QP 绑一个 rkey,发帧时查表盖进 RETH
imm_dataimm对应(包装层用 {req_2.offs[3:0], req_2.len} 拼凑,隐契约)
wr_id(完成 cookie)—无;完成只带 pid,靠顺序对应(§6)
send_flags(SIGNALED/INLINE/FENCE)约等于 lst 一个位lst 粗略对应 SIGNALED:不置位则不计完成、不发 cq ack(lynx_pkg.sv:348 注释)
(post 到哪个 QP,不在 WR 里)qpn 显式字段且是 {vfid,pid} 复合编码,不是线上 QPN(经 conn 表翻译)
—host / offsverbs 没有的 Coyote 内部管线字段;offs 是流控盖的重传槽号(rdma_flow.sv:130)

三个实质性差异,各连着一个 Stage B 发现

差异① 抽象层级降一级:消息 → 报文(→ 发现 B4)。verbs WQE 说"把这 8KB 写过去",HCA 传输层自己切报文;txMeta 的 opcode 直接就是线上报文 opcode,于是 >PMTU 切分成了 SQ 生产者的职责。Stage B 的 write8k 用例必须下发 WRITE_FIRST(4096)+WRITE_LAST(4096) 两条预切分命令,直接喂 8KiB WRITE_ONLY 会产出协议非法帧。且 FIRST 帧的 RETH.DMALen 是本命令长度(4096)而非 IBTA 语义的总消息长度(8192)——与严格接收方(CX-5)互操作时的观察项。

差异② 稳定字段搬进"三表"(→ Stage A 发现 5 / 三表语义)。verbs 把 rkey 放进每条 WR(一个 QP 可访问多个远端 MR);fns 简化为一 QP 一 rkey,连同 PSN、对端信息一起进配置表。verbs 里分散在 ibv_modify_qp 和每条 WR 里的信息,fns 重新分配为:

qp_interface   {vaddr, rkey, lpsn, rpsn, qpn, state}   ← rkey 在这!≈ modify_qp 的传输参数
conn_interface {udp, rip, rqpn, qpn}                    ← ≈ 地址向量 / 路径信息
txMeta         {opcode, qpn, laddr, raddr, len, imm}    ← 只剩每次都变的部分

差异③ 保护/完成机制整体缺席(→ §5 §6)。无 MR、无 lkey/rkey 本地校验、无 wr_id、无 SG。fns 实现的是 RC 传输层的线上行为(PSN/ACK/重传/ICRC),verbs 的资源管理层由使用者兜底——完整 Coyote 用 shell 兜,本平台用 doorbell + 构造兜。

TB 用线上 opcode 直接下命令并得到教科书反应:roce-rtl-sim/tb/tb_stage_b.sv:381-392(0x06/0x08/0x0A);回灌 ACK opcode=0x11、PSN 跳变得到 AETH syndrome 0x60 的 NAK(Stage B 报告 §5.4)。

§4 dreq_t 的双端点设计与 B2 案例

4.1 一条命令,两个端点描述符

Coyote 的 SQ 是通用命令口(本地拷贝/卸载/TCP/RDMA 同一格式),世界观是"任何搬运有两个端点,各配一份完整描述符"(roce-rtl-sim/rtl/pkg/lynx_pkg.sv:362-365):

typedef struct packed {
    req_t req_1; // rd, local   ← 本地端:数据从哪来(WRITE 时 = staging laddr)
    req_t req_2; // wr, remote  ← 远端:数据到哪去(WRITE 时 = raddr → RETH VA)
} dreq_t;

TB 的构造一目了然(roce-rtl-sim/tb/tb_stage_b.sv:311-330):填好 req_1 后整体复制给 req_2,再只改 vaddr。"local/remote"的分工恒定,变的只是读写方向——支持 RDMA READ 时填法不变。

包装层把 256 位 dreq_t 压成 248 位 txMeta 时,从两半各摘所需;远端地址 64 位中只有 48 位是真地址,高 16 位被征用为 {10'b0, strm, dest} 并原样上线(RETH VA 高位)——对端 shell 靠它决定数据落到哪条流。这就是 RADDR 签名值从 64 位重新注册为 48 位(0x334455667788)的原因。

4.2 B2 案例:一个 struct 身上的两套顺序

B2:laddr/raddr 在包装层与 HLS 之间互换。症状:帧其余 116 字节全对,唯 RETH VA 全零。任何编译器、lint、单侧仿真都不报警——类型全对(都是 64 位)、握手全对。

根因是同一个 struct 同时存在两套"顺序",两个世界各信了一套:

struct txMeta {
    ...
    ap_uint<64> raddr;     // ① 声明序:raddr 在前 → 物理布局 [119:56]
    ap_uint<64> laddr;     //          laddr 在后 → 物理布局 [183:120]
    ...
    txMeta(..., ap_uint<64> laddr, ap_uint<64> raddr, ...)   // ② 参数序:laddr 在前!
        : ..., raddr(raddr), laddr(laddr), ... {}             // ③ 按"名字"赋值
};
世界信息靠什么传递结果
csim(C++)名字:构造函数按名字赋值(③),引擎按名字取 meta.raddr参数序②再乱也永远正确 → Stage A 全绿,雷安然埋着
RTL(综合后)位号:名字蒸发,只剩 TDATA[247:0];csynth 按声明序①解码(先声明在低位)上游 Coyote 手工打包时错把参数序②当字段顺序 → laddr 的值装进了 [119:56]

于是引擎从 [119:56] 解出的"raddr"其实是 laddr(=0),RETH VA 全零。修复即本仓库 roce-rtl-sim/rtl/coyote/roce_stack.sv:100-105 的 STAGE-B FIX:按声明序回装。

三种位序约定同场,是这类 bug 的温床:Vitis HLS 聚合(先声明在低位)、SV packed struct(先声明在高位)、Coyote 手工按位偏移。跨语言位级契约的唯一权威是"决定物理布局的那套规则";参数序、注释、变量名等源码便利层没有约束力。Stage C 规范:打包一律从声明序推导,最好直接对照 csynth 生成的解码位切片,并用签名值回归(给 raddr/laddr 各喂独一无二的值,看帧里各自落在哪)。
顺带解释布局里的"空洞":ibOpCode 是 enum → 占 32 位,所以 opcode 只用 [4:0]、qpn 却从 bit 32 开始——读打包代码时的 [31:5] 空段不是 bug,是 enum 填充。

§5 保护机制的三种形态:钥匙 → 地图 → 构造即安全

verbs"钥匙"Coyote"地图"本平台"构造"
机制MR 注册产生 lkey/rkey;每次访问验钥匙真·虚拟内存:getMem 映射 → 驱动填 shell 里的 TLB;DMA 前做 vaddr→PA 翻译;未映射 → 缺页由驱动处理固定 URAM staging 物理缓冲;单 QP 单租户;地址空间就那么大
隔离单位PD(保护域){vfid, pid}:每 vFPGA 区域 × 每 Coyote 线程一个地址空间(HPID 跟着请求走)无第二租户,无需隔离
拒绝形式校验失败 → NAK(Remote Access Error)TLB 无翻译 → 缺页/失败不存在拒绝路径;越界即回卷(TB 模型里 & (MEM_BYTES-1))

两个语义要点:

  • rkey 在线上是"摆设化"的:协议要求 RETH 携带 rkey,fns 发送侧从 QP 表查出盖章;但接收侧的实际防线不是验钥匙——完整 Coyote 里是落地时的 MMU 翻译,本平台则完全无校验(Stage B rx_loop 实测:放置命令的 vaddr 就是 RETH VA 原文,roce_stack 层不做任何检查)。
  • 与 B5 同构:RX 侧 ICRC 校验也被分支硬编码禁用(third_party/fpga-network-stack/hls/crc/crc.hpp:38 无条件 #define DISABLE_CRC_CHECK)。环回实验无碍(两端都是自己),接商品 RNIC 时对端会验我们的 TX(没问题),但我们的 RX 不设防——保护降级是这条分支的一贯姿态,不是孤例。
Coyote 侧证据(渲染包中保留的类型参数):roce-rtl-sim/rtl/pkg/lynx_pkg.sv:84-96 的 TLB 两级页表参数(TLB_S_ORDER=10 小页 / TLB_L_ORDER=9 大页 / N_TLB_ACTV=16)、lynx_pkg.sv:114 的 HPID_BITS=32。这些类型能被渲染出来,本身就说明完整 shell 的虚拟内存服务是一等公民。

§6 完成机制的三种形态:CQE+cookie → 计数器 → 32 位 ack_t

verbsCoyote本平台
形态CQE 队列条目,携带 wr_id cookiecq_* 接口 + 按 pid 的 checkCompleted 计数器m_rdma_ack 上的 32 位 ack_t(last 门控入队,B8)
对号方式cookie 乱序对号"发了几个 / 完成了几个"顺序对应同左;Stage C 起锁存为 AXI-Lite CQE 读回寄存器,布局按 ack_t
触发粒度SIGNALED 标志逐 WR 控制last 位 = "要不要计一次完成":不置位则流尾无 tlast、不增计数、不发 cq ack(lynx_pkg.sv:348 注释原文)
B8 的教训:rdma_flow 的 CQ 队列只搬 32 位 ack 本体、由 data.last 门控入队(roce-rtl-sim/rtl/coyote/rdma_flow.sv:143-145)。TB 最初按 33 位 dack_t 解读,所有字段整体错 1 位。设计 CQE 读回寄存器时按 ack_t 布局,别按 dack_t。

另一个容易踩的形态差异:fns 的五个调试计数器(tx/rx/crc_drop/psn_drop/retrans)是 ap_vld 脉冲语义——值只在 valid 拍有效。TB 必须锁存(roce-rtl-sim/tb/tb_stage_b.sv:55-61),上板后同理要用 AXI-Lite 寄存器锁存;且 crc_drop 在本分支恒 0(B5),文档必须加注。

§7 Scatter/Gather:被"搬走"而不是被"删掉"的自由度

verbs 的 sg_list 是 ibv_sge {addr, length, lkey} 数组,num_sge 为项数,语义随方向而变:

  • 发送 = gather(聚集):线上一条消息 = 各段本地缓冲按序拼接。典型:应用头在缓冲 A、payload 在缓冲 B,网卡发送时自己按序读两处拼成连续消息——零拷贝。
  • 接收 = scatter(散布):入帧按序填进列出的各段缓冲。
  • 每个 SGE 自带 lkey(各缓冲可属不同 MR)——"钥匙"模型的一贯性。

fns 为什么敢砍成恒 num_sge=1?因为数据接口是流式的。payload 不是引擎去内存里各处捡,而是用户一拍一拍推进来的(B3:提交 WR 后必须立刻主动推流,rdma_mux_retrans 对 WRITE 只登记序列+发重传缓冲写命令,m_rdma_rd_req 仅在 READ 响应时发出;Coyote 源码注释原话:"Shouldn't it be automatically delivered to the stack?")。在流式世界里 gather 是伪需求——谁产生这条流,谁就有机会在推流之前把任意几块内存拼好。

对 Stage C / P4 的设计输入:SG 的自由度没有消失,只是从"WQE 里的描述符列表"搬进了"推流机的实现"。将来 codec 场景若需"压缩头 + 压缩数据"两段拼接发送,不用改 SQ 格式——doorbell 的推流控制器按序读两个 staging 区间即可,你自己就是 gather 引擎。

§8 取舍总结:为什么敢砍、代价是什么、谁兜底

8.1 砍的理由(每条都有前提)

被砍机制敢砍的前提形态转移到
lkey/MR 校验生产者可信(自家 shell / 自家 doorbell),单租户Coyote:TLB;本平台:固定 staging 构造
逐 WR rkey一个 QP 只对一个远端缓冲区(应用模式简单)QP 上下文表(一 QP 一 rkey)
HCA 切分器SQ 生产者愿意遵守"报文级契约"Coyote:shell 的 dreq_rdma_parser_wr;本平台:doorbell 内置切分器(B4)
SG 列表数据通路是流式的推流机实现(§7)
CQE + wr_id完成天然按序(RC 顺序语义 + 单飞/浅流水)计数器 / 32 位 ack_t(B8)
RX ICRC 校验(存疑——更像分支的省事之举,B5)无;接商品 RNIC 时 RX 不设防,需知情

共同的动机是 FPGA 现实:逐 WR 校验逻辑、TLB、CQE ring 都是面积与时序;fns 的目标是把 RC 传输层数据通路做进可综合的 HLS,资源管理留给载体。这与本平台"数据通路原型优先"的目标一致。

8.2 代价:契约取代校验,而契约没有机器检查

砍掉运行时校验后,正确性靠约定维持——而约定散落在结构体声明序、打包代码、源码注释里,编译器和仿真器都不替你检查。Stage B 抓获的三条缝(B2 打包序、B3 推流契约、B4 切分契约)全部位于 fns 与 Coyote 的交界面上,单独测任何一方都测不出来。这正是 Stage B 作为独立阶段存在的理由,也是三件补偿性工程的由来:

  1. 手册化规范:打包以声明序为准;WQE 提交后立刻推流;大 WR 预切分 ≤PMTU;CQE 按 ack_t 布局(Stage B 报告 §7 移交清单)。
  2. 签名值回归:每个字段喂独一无二的值,帧内容逐字节对拍 golden(check_golden_icrc.py 入库复用)。
  3. 独立参考实现:ICRC 用零共同血统的 30 行 Python 双算互证;它还能构造电路造不出的"合法坏帧"(负测试)。

8.3 谁兜底:doorbell 的真实身份

把 §1–§7 收拢成一句话:本平台的 doorbell 不是 verbs 的 post_send,而是"post_send + HCA 传输层切分器 + 三表管理者 + gather 推流机"四合一。它要补的正是 txMeta 与真 verbs WQE 之间的全部差距——这份差距清单,就是 Stage C 的需求规格。

§10 L2 三条路与 CX-5 站落点(2026-07-23 决策)

Stage D 的帧从 IPv4 打头、线上没有一个 Ethernet 字节 —— 这不是缺陷,是接缝:在完整 Coyote 里,roce_stack 的下游本来就站着 fns 自家的 L2 封装站(third_party/fpga-network-stack/hls/mac_ip_encode/),Stage D 选择裸 CMAC 环回时把这一站(连同 ARP/ICMP)整体省掉了。环回两端同栈:没有对端要 MAC、没人发 ARP 查询,一个字节的 L2 都不需要。补口的三条候选路线与判定:

路线内容判定
fns 自家套装mac_ip_encode(TX 造头:ARP 查表 + 子网/网关路由判断)+ ip_handler(RX 剥头分流,自带专用 m_axis_ROCE 出口)+ arp_server_subnet + icmp_server + ethernet_frame_padding_512✅ 选定 —— 同门血统、512 位被 Coyote 100G 生产部署验证、dataIn 格式与 roce_stack.m_axis_tx 零适配;白送标准 ARP 应答与 ping 可达性(联调时把 L2/L3 问题与 RDMA 问题解耦)
verilog-ethernet eth_axis_tx/rx纯 RTL 造头/剥头 + 双端静态 MAC 配置备胎:最轻,但无 ARP/ICMP,CX-5 主机侧需手配静态邻居表
Corundum 作载体整 NIC 框架❌ 不可行(过重、架构不匹配,此前已论证)

落点:CX-5 互操作站开工时插装;Stage D 保持认证态不动。理由:① 环回里 L2 三大功能(DMAC 查表 / ARP / 路由判断)全部空转,收益为零;② 集成需 csynth 多个 HLS IP + 时序重收敛 + 重出 bit + golden 口径重定(TX capture 会多 14 字节帧头,校验链全得动),等于 Stage D gate 全套重考;③ post-route 认证件(stage_d_shell/syn/proj/out_stage_d_certified/impl.dcp 与配套 .bit)作废,阶段审计链被搅乱。

勘误(2026-07-23 实测):此前"本仓库只快照了 fns 的 rdma/ 子集、届时需重新 clone"的说法作废 —— third_party/fpga-network-stack/hls/ 下 mac_ip_encode / ip_handler / arp_server_subnet / icmp_server / ethernet_frame_padding_512 五件套源码全部在仓(ls 实测确认),无需任何外部拉取。
