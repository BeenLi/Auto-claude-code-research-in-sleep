阅读前提。本文假定你已理解:#pragma HLS DATAFLOW 把函数调用变成并发常驻硬件进程、进程间只靠 hls::stream 通信、顶层 rocev2_top 是 ap_ctrl_none 自由运行核。本文聚焦一个问题:那条连接进程的管道,它的"深度"意味着什么、如何决定、错了会怎样。

1. 一行 pragma 的两种命运

同一行代码:

static stream<net_axis<WIDTH> > rx_exh2dropFifo("rx_exh2dropFifo");
#pragma HLS STREAM depth=32 variable=rx_exh2dropFifo

在两条工具链路径上,结局完全不同:

1.1 csim:pragma 被当作注释丢弃

csim 的构建就是普通 clang 编译(见 stage_a_csim/work_gui/hls/hls/csim/build/csim.mk:clang-16 -std=gnu++17 ... -Wno-unknown-pragmas,最后链接成 csim.exe)。此时 hls::stream 是头文件里的一个软件类,底层是无界队列:

  • .write() = push,永不阻塞、永不失败 —— 写一万个也照收;
  • .read()/.empty() = pop / 判空 —— 空的一侧是忠实建模的;
  • .full() 恒为假 —— depth=32 这个数字没有任何运行时效力。

1.2 RTL:每条 stream 物化为一个 Verilog FIFO 模块

综合之后,每条内部 stream 变成一个真实的 FIFO 实例。本仓库 roce-rtl-sim/rtl/hls/ 下就躺着综合产物 —— 49 种 FIFO 模块,命名规则一目了然:rocev2_top_fifo_w宽度_d深度_存储风格。三条我们重点讨论的 FIFO,其 pragma → 物理模块的映射在顶层 rocev2_top.v 里可以逐字验证:

C++ 里的 stream(pragma)顶层 RTL 实例(实测)说明
rx_exh2dropFifo depth=32
元素 net_axis<512>(577 逻辑位)		rocev2_top_fifo_w1024_d32_A rx_exh2dropFifo_U(...)工具将 577 位负载对齐打包为 1024 位存储
tx_pkgInfoFifo depth=128rocev2_top_fifo_w64_d128_A tx_pkgInfoFifo_U(...)包描述符队列
rt_freeListFifo depth=META_TABLE_SIZE(=2000)rocev2_top_fifo_w16_d2000_A rt_freeListFifo_U(...)16 位指针 × 2000 格
出处:roce-rtl-sim/rtl/hls/rocev2_top.v(grep 实例名即可复现)。

结论先立住:depth 是一份"物理容量合同",只有 RTL 才兑现;csim 对它的全部态度是 -Wno-unknown-pragmas。这决定了后文所有"csim 测不出"的病灶。

2. FIFO 的物理解剖

2.1 端口与握手

打开任意一个生成的 FIFO 模块(如 roce-rtl-sim/rtl/hls/rocev2_top_fifo_w24_d2_S.v),接口就是流控的全部真相:

// 写侧(生产者可见)
output if_full_n;     // 低 = 满,生产者必须停 —— 背压的源头
input  if_write;
input  [W-1:0] if_din;

// 读侧(消费者可见)
output if_empty_n;    // 低 = 空,消费者必须等
input  if_read;
output [W-1:0] if_dout;

// FRP(First-Read Protocol)辅助
output if_num_data_valid;  // 当前占用格数
output if_fifo_cap;        // 总容量

C++ 里的 !s.empty() 综合成对 if_empty_n 的采样;而 C++ 里你从来不写的那半句 —— "写之前看看满不满" —— 综合器替你补上了:进程的流水线在 if_full_n 为低时整体停摆(stall)。这就是为什么 C 源码里看不见背压,但硬件里处处是背压。

2.2 穿越延迟:write → read 至少 1 拍

模块头部注释写着 //RAW latency 1:本拍写入的数据,下一拍才能被读侧看到。所以 dataflow 网络里每一跳 FIFO 至少贡献 1 个周期的固有延迟 —— TX 路径十几跳串下来就是十几拍,这是 csim(同一次调用内 push 完就能 pop)完全不体现的。

2.3 存储介质:后缀 _S / _D / _A 的含义(实测)

后缀MEM_STYLE(模块内参数实测)物理映射本设计中的使用规律
_S"shiftReg"SRL16/SRL32 移位寄存器(LUT 内)浅 FIFO:d2 / d3 / d4
_D"distributed"LUTRAM(分布式 RAM)中等:如 w145_d16、w50_d32
_A"auto"工具按 宽×深 自选(大者落 BRAM)d8 以上多数;w16_d2000 必然落 BRAM

粗算两笔账,感受"深度不是免费的":

  • rt_freeListFifo:16 bit × 2000 = 32 Kb ≈ 正好一块 BRAM36(18b×2048 模式,36.9 Kb)。一条 pragma,一块 BRAM。
  • rx_exh2dropFifo:1024 bit × 32 = 32 Kb —— 容量相同,但形状极宽极浅。若映射成 BRAM,受 BRAM36 最大 72 位口宽限制要并联 ~15 块、每块只用 32/512 深度,浪费 >90%;所以 auto 在这种形状下通常选 LUTRAM/寄存器。同样的 bit 数,"形状"决定资源代价 —— 这就是为什么加深一条 512 位数据 FIFO 远比加深一条 16 位指针 FIFO 昂贵。

3. 流控的两侧:csim 只建模了一半

empty 侧(消费者流控)full 侧(生产者流控 / 背压)
RTLif_empty_n:空则消费者等if_full_n:满则生产者 stall,stall 沿上游链式传播
csim✅ 忠实:.empty() 真实判空❌ 缺失:无界队列永不满,depth 无效

由此产生 stream depth 的第一定律:

凡是错误症状要经由"FIFO 满"才能表达的 bug —— 降速、stall 链、死锁 —— csim 一律绿灯放行。你可以把本设计里任何一条 depth=32 改成 depth=2,csim 结果一个字节都不会变;差别只在 RTL 里爆发。

但 csim 并非对深度问题毫无用处 —— 它在退出时会"坦白":

INFO [HLS SIM]: The maximum depth reached by any hls::stream() instance
                in the design is 1999

这是 csim 对每条 stream 的峰值占用做的记录(它自己不限深,但它记账)。这个数字怎么用、有什么坑,见下一节的法证案例与 §7 方法论。

4. 法证一例:csim 报告里的"1999"是谁

本仓库 Stage A 的 csim 日志(stage_a_csim/work_gui/hls/hls/csim/report/rocev2_top_csim.log)结尾有两条与 FIFO 有关的输出:

WARNING [HLS SIM]: hls::stream 'rt_freeListFifo' contains leftover data,
                   which may result in RTL simulation hanging.
INFO    [HLS SIM]: The maximum depth reached by any hls::stream() instance
                   in the design is 1999

两条都指向同一条 FIFO,而且数字能精确对账:

4.1 rt_freeListFifo 是什么:FIFO 用作"自由列表"

看 third_party/fpga-network-stack/hls/ib_transport_protocol/retransmitter/retransmitter.hpp:

const uint32_t META_TABLE_SIZE = 2000;                       // :35
#pragma HLS STREAM depth=META_TABLE_SIZE variable=rt_freeListFifo  // :595

// freelist_handler —— 上电预填 + 回收 (:557-566)
if (!rt_releaseFifo.empty()) {
    rt_freeListFifo.write(rt_releaseFifo.read());            // ACK 后归还指针
} else if (freeListCounter < META_TABLE_SIZE && !rt_freeListFifo.full()) {
    rt_freeListFifo.write(freeListCounter);                  // 初始化:灌入 0..1999
    freeListCounter++;
}

// 插入重传条目时消费 (:341-343)
else if (!tx2retrans_insertRequest.empty() && !freeListFifo.empty()) {
    newMetaIdx = freeListFifo.read();   // 取一个空闲槽位指针

这条 FIFO 里装的不是数据流,而是重传元数据表的空闲槽位指针池:上电灌满 2000 个指针;每挂起一个未确认的 WR 取走一个;对端 ACK 后归还。FIFO 的占用数 = 当前空闲槽位数。

4.2 对账:2000 − 1 = 1999

  1. TB 全程只发了一个 WRITE → 只发生一次 inserting new meta ... occupying pointer 0x0(日志可查),消费 1 个指针;
  2. TB 从不回 ACK → 指针永不归还;
  3. 预填循环共写入 2000 个;峰值占用 = 2000 写 − 1 读 = 1999,与工具报告分毫不差。

一条匿名的工具统计,就此指认了具体 FIFO。这也演示了"csim 峰值占用报告"的正确读法:它是占用画像,不是错误告警。

4.3 顺带纠一个错

本文档作者(Claude)在此前的对话中把 leftover data 警告解读为"重传互锁状态没归位、cosim 的头号拦路虎"。读完 freelist 源码应当修正:对这条 FIFO 而言,结束时非空是设计使然 —— 自由列表非空恰恰意味着"还有空闲槽位",是健康状态。该警告是工具的通用启发式(任何残留都报),对 数据 FIFO 是真告警,对 池类 FIFO 是误报。读这类警告,必须先问:这条 FIFO 的语义是"流"还是"池"?

5. depth 分类学:本设计 89 条 pragma 的五个层级

把 ib_transport_protocol.cpp(75 条)+ rocev2.cpp(14 条)的全部 STREAM pragma 按深度统计:

d2 ×58
d4 ×13
d8 ×8
d16 ×2
d32 ×4
d64 ×2
d128 ×1
d2000 ×1

分布不是随机的 —— 每个深度档位对应一种截然不同的设计意图。逐层解剖:

Tier 1 depth=2 —— 弹性解耦(全场 65%)

两格是让相邻两个 II=1 进程互不卡死对方的最小配置:一格正被下游读,一格供上游写,吸收 1 拍握手抖动。它不为存数据,只为切开时序与控制耦合 —— 相当于数字设计里的 skid buffer。典型:rx_crc2ipFifo、stateTable2txIbh_rsp 这类逐字/请求-响应通道。物理上全部落 _S(SRL),近乎免费。

为什么不是 depth=1?单格 FIFO 无法同拍读写并行,会把两个 II=1 进程降速到隔拍工作;两格是维持满线速的最小值。这也是 Vitis 把 stream 默认深度定为 2 的原因。

Tier 2 depth=4~8 —— 微观抖动吸收

出现在包头拼接/移位对齐路径:tx_shift2ibhFifo(d8)、rx_exh2rethShiftFifo(d4)等。这些进程不是每拍恒定一进一出 —— 拼头时会"憋两拍再连吐两拍"(回忆 APPEND PAYLOAD 的 HEADER→RETH_PAYLOAD→INFO 状态机)。深度 4~8 吸收这种拍级突发,避免瞬时波动传成上游 stall。判据:进程的"进出节奏差"有几拍,就给几格余量。

Tier 3 depth=16~32 —— fork-join 重汇聚偏差(最关键、最易错)

这是 dataflow 设计里 bug 密度最高的档位。看本设计最典型的一处 —— RX 方向的 PSN 检查 / 乱序丢弃结构(拓扑摘自 ib_transport_protocol.cpp:2540-2600):

尺寸法则(本档位的核心公式):

快路径缓冲深度 ≥ ⌈慢路径最坏延迟(拍)⌉ × 快路径速率(元素/拍) + 握手余量

这里数据路每拍可到 1 个 512 位字;判决路要过 d2 meta FIFO → rx_ibh_fsm 状态机 → 状态表 BRAM 读 → 判决 FIFO,最坏十几拍。depth=32 ≈ 判决延迟上界 × 1 字/拍,再留一倍工程余量。

违反的后果分两级:轻则数据路 FIFO 频繁写满 → 背压沿 exh→shift→ibh→udp→ip→crc 一路传回 MAC 口,吞吐塌陷;重则若背压环住了判决路本身依赖的资源(见 §6 死锁环),整网冻结。同档位的 tx_appMetaFifo(d32,软件下发的 WR 队列)、rx_ackEventFifo(d32,ACK 事件突发)同理。

Tier 4 depth=64~128 —— 速率解耦 / 在途事务(Little 定律)

这一档的 FIFO 面对的不再是"拍级抖动",而是两个子系统之间的延迟×吞吐乘积。用 Little 定律 N = λ × T(需要的在途量 = 速率 × 往返延迟)来读:

FIFOdepth解读
rx_remoteMemCmd64RX 侧向主机内存发写命令。要在内存往返延迟 T 拍内维持线速,必须允许 λ×T 条命令在途。d64 允许 64 条未完成命令 —— 覆盖小消息(1 命令/包)高速率场景。
tx_pkgInfoFifo128TX 侧每包写一条 pkgInfo(类型, 字数) 给 CRC 级(ib_transport_protocol.cpp:1168-1207)。包描述符必须先于包体到齐,CRC 才知道边界;d128 = 允许 128 个包的描述符先行排队,把"描述符生产"与"包体穿过整条 TX 流水线"彻底解耦。
识别特征:这一档 FIFO 的元素是"命令/描述符"而非数据字,宽度窄(w64、w152),加深便宜;它们的深度编码的是系统级并发度(允许几个包/几条命令在飞),不是路径延迟差。

Tier 5 depth=池容量 —— FIFO 即数据结构

rt_freeListFifo(d2000 = META_TABLE_SIZE)不在"缓冲"谱系里 —— 它是把 FIFO 直接用作并发安全的数据结构:自由列表 / 信用池。深度 = 池的全集大小,一格都不能少(否则初始化灌不满,凭空丢槽位)、多了纯浪费。同类惯用法:令牌桶、credit-based 流控的 credit 池、预分配缓冲句柄池。识别特征:上电预填、取走-归还成对、占用数有业务含义(此处 = 空闲重传槽数)。它的深度跟着数据结构常量走(META_TABLE_SIZE),与流水线时序完全无关。

6. 两种病理:欠深与过深

6.1 欠深病理 A:吞吐气泡(常见、隐蔽)

FIFO 未满时不影响任何行为;一旦频繁写满,生产者 stall,stall 逐级上传。症状是带宽上不去而非功能错误 —— 数据全对,速率减半。csim 完全无感;cosim 波形里表现为 if_full_n 周期性拉低、上游 TREADY 抖动。

6.2 欠深病理 B:死锁环(致命)

dataflow 网络死锁的形式条件:进程等待图中出现环 —— 环上每条边要么是"等上游给数据"(empty-wait),要么是"等下游腾空间"(full-wait)。fork-join 欠深是最经典的成环方式。把上图的 ★ 假想改成 depth=2 推演一遍:

  1. 一个 64 字的包进入。rx_process_exh 写出 2 个字后,rx_exh2dropFifo 满 → full-wait,停;
  2. 它停了,就不再从上游 rx_shift2exhFifo 读 → 上游链条逐级写满、逐级停;
  3. 若 rx_ibh_fsm 的判决恰好依赖被卡进程尚未转发的信息(例如 meta FIFO 也在被堵的链条上),判决永远发不出 → drop_ooo_ibh empty-wait,永等;
  4. 环闭合:exh 等 drop 腾空间 ← drop 等判决 ← 判决等被 exh 堵住的上游。全网冻结,无任何错误信号。
死锁的狡猾之处:它只在"包长 > 快路径深度 且 判决延迟 > 某阈值"同时成立时触发 —— 小包测试全过,某天一个大包让系统当场石化。csim 永远绿灯(无界),小流量 cosim 也可能漏过。这就是 depth 审计必须按最坏情形分析而不是靠测试碰的原因。

6.3 过深病理:资源、时序与"掩盖"

  • 资源:§2.3 的账 —— 一条 512 位数据 FIFO 每加深 64 格 ≈ 32 Kb 存储。全设计 89 条 FIFO,深度普涨一档,BRAM/LUTRAM 预算立刻可见地恶化。
  • 掩盖设计病:更隐蔽的害处 —— 把本该修拓扑的问题(判决路径太长、反馈环太深)用"加深扛过去"。深 FIFO 里长期高水位 = 系统在用缓冲抵消结构性速率失配,PMTU 一改、时钟一改就复发。先问"为什么会积压",再问"加几格"。
  • 延迟:对延迟敏感路径(此处的 ACK 环路),深 FIFO 中的排队直接计入 RTT,进而影响重传定时行为。

7. 工程方法论:depth 到底怎么定

7.1 分析法(设计时,主方法)

对每条非 d2 的 FIFO 回答三个问题,对号入座五个层级:

  1. 它是流、是队列、还是池? 池 → 深度=池容量(T5);队列 → Little 定律(T4);流 → 下一问;
  2. 它在 fork-join 的快路径上吗? 是 → 深度 ≥ 慢路径最坏延迟 × 快路径速率(T3);
  3. 生产/消费的拍级节奏差几拍? 突发拼头类给 4~8(T2),纯逐字给 2(T1)。

7.2 实验法(验证与校准)

手段能给什么局限
csim 结束时的 max-depth 报告(§4)C 语义下各流峰值占用的下界画像;池类 FIFO 的占用对账无背压 → 占用被低估或畸变;只报全局最大值不报逐条(逐条需看 cosim)
cosim + 通道剖析(Dataflow/Channel Profiling,报告每条 FIFO 峰值占用与满/空 stall 拍数)真握手下的逐条占用画像;直接指出常满(欠深)与常空(过深)的通道只覆盖测试激励走到的场景;最坏情形仍靠分析
cosim 死锁检测(挂死时报告等待环上的进程与 FIFO)死锁环的直接指认事后诊断,且要激励能踩中
板上 ILA 采 if_full_n/prog_full真实流量下的背压统计综合迭代慢,放最后

7.3 本仓库现成的一条验证路径

roce-rtl-sim/ 已有综合出的 RTL 与仿真脚手架 —— 最有教学价值的实验:把 rx_exh2dropFifo 的 depth 从 32 改小(如 4),重跑 csim(预期:全 PASS,一字节不变)再跑 RTL 仿真(预期:大包场景吞吐塌陷或挂死)。一次实验同时坐实 §3 第一定律与 §6 死锁推演。
